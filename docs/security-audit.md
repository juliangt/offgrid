## Executive summary

The architecture's core claim — **nodes and mules only ever handle opaque envelopes; all cryptography happens on the client** — holds end to end: it was verified in the daemon (§1.1: no crypto exists server-side, admission is shape-only, storage is verbatim), in the shipped client engine (§2.1: no egress beyond three fixed endpoints carrying public/ciphertext data, secrets confined to IndexedDB), and claim-by-claim against the protocol's own threat model (§3.3: no §13 claim remains that the code does not uphold). The audit produced **30 findings: 0 critical, 0 high, 6 medium, 10 low, 14 info**. Of these, **17 were fixed or corrected in this PR** — 9 code/verification fixes (NODE-01/02/03, SPA-01/02/06, PI-01, SUPPLY-01/03), 7 normative-spec corrections (PROTO-01..07, protocol.md 1.12.2, documentation-only) and PROTO-08 partially (§-contract amendment deferred) — **12 are documented accepted risks or documentation records** (NODE-04/05/06, SPA-03/04/05, PI-02/03/04, SUPPLY-02/04/05), and **1 was already mitigated** by the protocol-assigned Track 1 shields (NODE-07). The headline corrections: **PROTO-01** — the spec's claim that hint rotation decays directory-holder linkability was wrong: the epoch is a public counter and `created_at` rides plaintext in every envelope, so a directory holder can recompute any epoch's hint and link envelopes to aliases permanently (protocol §13.3/§6.1 corrected, spec 1.12.2; an accepted residual, not a closure); **NODE-01** — the directory table was the one unbounded, attacker-writable disk resource on the node; it is now capped (5000 rows, `429 node_full` shed on new registrations at cap); **PI-01** — IPv6 was unaddressed by every Track 1 shield, leaving a live link-local address as a side door around the per-source limits; it is now disabled on the client-facing interfaces. Disclosure note: all fixes and this report land in the same merge — there is no window between fix and disclosure.

## Severity scale

| Severity | One-line definition |
|---|---|
| **Critical** | Remote, unauthenticated compromise of the node process, or break of the blind-node/E2EE core claim (plaintext or key exposure). |
| **High** | Unauthenticated attacker causes service-wide outage, persistent data loss, or meaningful plaintext/metadata compromise with no practical mitigation in the shipped deployment. |
| **Medium** | A confirmed weakness an unauthenticated attacker can exploit with real (but bounded or recoverable) impact — degradation, poisoning, resource exhaustion — or one requiring specific positioning/conditions. |

## 1. Node daemon

Audited: `node/main.go`, `node/internal/api/` (handlers.go, middleware.go, ratelimit.go, health.go), `node/internal/storage/storage.go`, `node/internal/envelope/envelope.go`, `node/internal/cleanup/cleanup.go`, `node/internal/health/health.go`, `node/internal/status/` (engine.go, activity.go), `node/internal/sysres/`, `node/go.mod`/`go.sum` (hygiene only). Out of scope here: `node/web/` SPA internals (Phase 2), `node/internal/power/` and `sdnotify/` hardware plumbing (reviewed only for request-path impact — none: both run off-request-path).

### 1.1 The core claim, verified end to end

The claim under audit — **"nodes only ever handle opaque envelopes; all crypto happens on the client"** — holds in the code:

- **No cryptography exists in the daemon.** A source scan of `node/` finds zero imports of `crypto/*` (beyond stdlib hashing-free plumbing), `golang.org/x/crypto`, nacl/box, or any signature/decryption call outside comments. The storage layer stores the payload string verbatim (`storage.go` `InsertEnvelopes`, line 582) and returns it verbatim (`PullEnvelopes`, line 634); envelope admission is shape-only (`envelope.go` `Validate`, line 190: version set, hex id/hint regexes, timestamp window, TTL bounds, strict-Base64 payload decode for a [248, 400]-byte length check). The node never recomputes `id` (§6.2), never verifies signatures, never consults the directory on the push path (`handlers.go` `handleSync`, line 658 — the §10.5 unknown-recipient guarantee, pinned by `unknown_recipient_test.go`).
- **Round-trip fidelity is tested**: payload bytes survive a store/pull cycle byte-identical (`TestSyncPushPullDedup`, `tests/sync_e2e.sh` §3–4), and served envelopes never carry admission-time `meta` (§15.3, `TestSyncV2AdmissionDedupAndServing`).

### 1.2 Findings

#### NODE-01 — Medium — Unauthenticated, unbounded directory-table growth (persistent disk-fill DoS)

- **Severity:** Medium
- **Affected component (pre-fix):** `node/internal/storage/storage.go` `UpsertDirectory` (no cap) + `node/internal/api/handlers.go` `handlePostDirectory`; the §10.6 janitor (`cleanup.go` `sweep`) reaps only `envelopes`.
- **Description.** `POST /api/v1/directory` is unauthenticated and every accepted request permanently inserts or updates one `directory` row. Before this fix the table had **no row cap and no TTL** (the code itself noted "directory rows are never auto-deleted in Phase 1"). Every other persistent surface is bounded: envelopes have the 5000-row §8.1 cap; counters and rate-limit state are RAM-only. The directory was therefore the one unbounded, attacker-writable disk resource: at ~150 B per bare entry and ~2.2 KiB with a max-size §4.6 prekeys bundle, sustained registrations (the §10.1 request budget permits ~30/min per IP indefinitely; colluding stations multiply) grow the SQLite file without bound until the SD card fills — after which every envelope push sheds `507 storage_unavailable` (the clean shed keeps the daemon alive, but the mailbox stops accepting mail) and the card keeps wearing. The janitor never recovers it: operator intervention (deleting rows) would be required on a node class with no SSH (A8). `GET /api/v1/health` would show `disk_free_low` and growing `db_size_bytes`, but nothing stops the growth.
- **Reproduction (pre-fix):**
  ```bash
  # from any station on the open Wi-Fi (repeat per colluding station):
  while :; do
    curl -s -X POST http://10.42.0.1:8080/api/v1/directory \
      -H 'Host: offgrid.local:8080' -H 'Content-Type: application/json' \
      -d "{\"alias\":\"j$RANDOM\",\"pubkey\":\"$(head -c 32 /dev/urandom | base64)\",\"x25519\":\"$(head -c 32 /dev/urandom | base64)\"}"
    sleep 2   # stays under the §10.1 request budget forever
  done
  # rows accumulate permanently; watch db_size_bytes climb in /api/v1/health.
  ```
- **Fix (in this PR):** a per-node directory cap mirroring the envelope cap's design:
  - `storage.go`: new `maxDirectoryEntries` var (5000, the §8.1 envelope-cap class; test hook, exported via `MaxDirectoryEntries()`, line 149/471). `UpsertDirectory` (line 713) first probes pubkey existence (cheap indexed lookup); an **existing** pubkey always refreshes — a full directory never locks registered users out of their own republication — while a **new** pubkey at/over the cap is rejected whole with `ErrCapacity` (fail closed; nothing stored). The exists-then-count order keeps the refresh path cheap and pays the `COUNT(*)` only for genuinely new rows; as with envelopes, the check and insert are separate statements, so a race may overshoot the cap by a couple of rows — irrelevant at a 5000-row bound and identical to the envelope path's documented ≤100 tolerance.
  - `handlers.go` `handlePostDirectory` (line 592): maps `ErrCapacity` to `429 {"error":"node_full"}` (line 616) — the same capacity shed `POST /api/v1/sync` already answers at envelope capacity, and a status class this endpoint already answers under the §10.1 request budget. No documented API shape changes; a valid registration below the cap behaves exactly as before (pinned by `TestDirectoryBelowCapAcceptsNewRegistrations`).
- **Regression tests:** `node/internal/storage/storage_test.go` `TestDirectoryUpsertCapacityGuard` (cap sheds new, refresh survives at cap, deleting a row re-opens capacity), `TestDirectoryUpsertDefaultCap` (5000 accepted / 5001st rejected / refresh at full cap); `node/internal/api/security_test.go` `TestDirectoryCapShedsNewRegistrationsWithNodeFull` (end-to-end: 429 node_full, nothing stored, existing entry refreshes 200), `TestDirectoryBelowCapAcceptsNewRegistrations`.
- **Status:** Fixed in this PR.

#### NODE-02 — Low — HTTP server missing read/write/idle timeouts (slow-body drip, idle-socket hoarding)

- **Severity:** Low (defense-in-depth: the reference deployment's Track 1 firewall connlimits — 32/source, 20 stations — bound the same attack; but the Track 2 premise is that the daemon must shed by itself when the shields are bypassed, `docs/hardening.md` §3)
- **Affected component (pre-fix):** `node/main.go` — the `http.Server` literal set only `ReadHeaderTimeout: 5s`; `ReadTimeout`, `WriteTimeout`, `IdleTimeout` were unset (net/http's zero value = no timeout).
- **Description.** `http.MaxBytesReader` bounds request-body *size* (1 MiB → 413, `middleware.go` `limitBody`, line 82) but not *time*. Pre-fix, a hostile station could (a) open a connection, send valid headers, then drip the body one byte per minute indefinitely — each drip connection holds a server goroutine and its buffers forever; or (b) complete one request per socket and then idle forever — keep-alive sockets were never reaped (`IdleTimeout` 0). Neither is stopped by the body cap, the per-IP request budget (which spends one token per *request*, not per open socket), or the 1 MiB header cap (431). On the Pi-class target this is connection/goroutine hoarding toward `MemoryMax=192M` and fd exhaustion; the daemon alone had no time bound on any of it.
- **Reproduction (pre-fix):**
  ```bash
  # slow-body drip — headers valid, body dribbled; pre-fix the connection
  # (and goroutine) is held indefinitely; post-fix ReadTimeout closes it at 60 s:
  { printf 'POST /api/v1/sync HTTP/1.1\r\nHost: offgrid.local:8080\r\nContent-Type: application/json\r\nContent-Length: 1000000\r\n\r\n{';
    while :; do printf 'A'; sleep 55; done; } | nc 10.42.0.1 8080
  # idle hoarding — complete one request, then hold the socket:
  exec 3<>/dev/tcp/10.42.0.1/8080   # pre-fix: held forever; post-fix: reaped at 120 s
  ```
- **Fix (in this PR):** `main.go` now builds the server through `newHTTPServer` (line 111) with the full timeout set: `ReadHeaderTimeout` 5 s (unchanged), `ReadTimeout` 60 s (whole request lifetime — orders of magnitude above any legitimate phone interaction on the node's own AP), `WriteTimeout` 60 s (covers the ~1 MiB worst-case directory GET at captive-portal speeds), `IdleTimeout` 120 s (above browser keep-alive habits). Sized to be invisible to honest clients — `tests/sync_e2e.sh` (383 assertions, real daemons) stays green.
- **Regression tests:** `node/main_test.go` `TestNewHTTPServerTimeouts` — pins all four fields and their sanity ordering, so a regression that silently drops one fails the suite.
- **Status:** Fixed in this PR.

#### NODE-03 — Low — Missing baseline security headers (nosniff, framing protection, referrer)

- **Severity:** Low
- **Affected component (pre-fix):** `node/internal/api/middleware.go` (no header middleware; the wrapper chain was `canonicalHost(limitBody(mux))`, `handlers.go` `NewWithCounters`).
- **Description.** The daemon set no security headers. Consequences, in increasing order of concern:
  1. **No `X-Content-Type-Options: nosniff`.** All bodies carry exact §10.1 Content-Types, but the directory GET serves client-controlled JSON verbatim inside `prekeys` (unknown bundle members are ignored and stored as-published, `handlers.go` `validatePrekeysBundle` line 539; served verbatim, `storage.go` `GetDirectory`) and `writeJSON` serializes with `SetEscapeHTML(false)` (`handlers.go`, `writeJSON`). With legacy UA MIME-sniffing in the picture, response re-interpretation was one browser quirk away; `nosniff` closes the class outright.
  2. **No framing protection.** The portal, guide and §10.7 operator status page ship their CSP as `<meta>` tags — and `frame-ancestors` is *ignored inside a meta policy*, so pre-fix clickjacking protection (relevant at least for the operator view, which displays operational detail) rested on nothing.
  3. **No `Referrer-Policy` header.** The pages set `<meta name="referrer" content="no-referrer">`; the header extends the guarantee to every response and to clients that ignore meta.
- **Reproduction (pre-fix):** `curl -sI -H 'Host: offgrid.local:8080' http://10.42.0.1:8080/ | grep -Ei 'nosniff|x-frame|referrer'` → no output.
- **Fix (in this PR):** new `secureHeaders` middleware (`middleware.go` line 53) sets `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` on every response, wired outermost — `secureHeaders(canonicalHost(limitBody(mux)))`, `handlers.go` `NewWithCounters` — so 200s, the §10.2 301, the probe 302 and all error shapes carry them. A header-level Content-Security-Policy is deliberately NOT introduced: the per-page meta CSPs are the normative policies and a header copy would be a drifting second CSP; frame protection — the one directive meta cannot express — is delivered by `X-Frame-Options`. Non-breaking: the portal is a top-level destination and never legitimately framed.
- **Regression tests:** `node/internal/api/security_test.go` `TestSecurityHeadersOnEveryResponse` — asserts all three headers on 200 HTML, 200 JSON, 200 asset, 404, 405, 400, the canonical-host 301 and the captive-probe 302.
- **Status:** Fixed in this PR.

#### NODE-04 — Medium — Directory upsert has no proof-of-possession: any station can hijack any identity's entry

- **Severity:** Medium
- **Affected component:** `node/internal/api/handlers.go` `handlePostDirectory` (line 592) + `node/internal/storage/storage.go` `UpsertDirectory` (line 713); inherent to the §10.3 wire contract.
- **Description.** Directory registration is keyed by the Ed25519 **public key alone**, with no signature, challenge, or any proof that the poster holds the matching private key. The public key is public data — the same node's `GET /api/v1/directory` serves it. A hostile station can therefore republish a victim's `pubkey` bound to the **attacker's** `x25519` key (and attacker prekeys): every subsequent sender who picks the victim from the directory encrypts to the attacker's key and addresses the matching hint; the victim silently stops receiving mail while the attacker decrypts it. E2EE does not help — the attacker *holds* the key material the mail was encrypted to.
  - This is **protocol-inherent, not a coding error**: a blind node cannot demand proof-of-possession, because verifying a signature over the registration body is exactly the cryptography §1 forbids the node from doing ("never verifies signatures — clients verify"). `docs/protocol.md` §13.5 (bundle paragraph) already acknowledges the hole for the malicious-**node** case: "the signature does NOT close the pre-existing hole that the node can swap any entry's `x25519` member (directory entries are not authenticated end-to-end in Phase 1); closing that (key transparency) is out of scope."
  - **Audit nuance (recorded for Phases 2–3):** the unauthenticated POST widens that documented hole from *a malicious node operator* to *any station in radio range* — strictly cheaper to exploit than the documented variant. Mitigations that exist are all client-side and must be verified in Phase 2: §4.6 `spk_sig` client verification (defeats swapped *bundles*, and a failed verification must downgrade to identity addressing with a UI warning), the §4.7 identity-QR in-person exchange (trust-on-sight), and — open question — the §1.8.0 changelog wording that the merged recipient picker lets "the directory supply the fresh key material when an entry exists", which, if it means directory x25519 overrides QR-pinned contacts, would extend this finding's reach to QR-verified contacts. Phase 2 must pin the picker's precedence.
- **Reproduction:**
  ```bash
  # 1. Victim's entry is public on the same node:
  curl -s -H 'Host: offgrid.local:8080' http://10.42.0.1:8080/api/v1/directory
  # 2. Republish the victim's pubkey bound to the attacker's key material:
  curl -s -X POST http://10.42.0.1:8080/api/v1/directory \
    -H 'Host: offgrid.local:8080' -H 'Content-Type: application/json' \
    -d '{"alias":"<victim alias>","pubkey":"<victim ed25519 pubkey, public>",
         "x25519":"<attacker x25519 pubkey>","prekeys":<attacker-signed bundle>}'
  # -> 200 {"status":"ok"}; future directory-trusting senders encrypt to the attacker.
  ```
- **Recommended fix (not auto-applied — breaking, and it crosses the blindness invariant):** any node-side closure requires either (a) node-side signature verification over a proof-of-possession member (a wire/protocol change and a §1 exception to be designed with extreme care — a *limited*, purpose-bound verification that never touches envelopes), or (b) a key-transparency layer (log/audit of directory history clients can check), both explicitly out of scope for Phase 1 per the protocol. Interim client-side duties for Phase 2: verify bundle signatures before prekey addressing (normative already), surface trust warnings on first-seen key changes, and resolve the QR-vs-directory precedence question above.
- **Status:** Documented / accepted risk (protocol-inherent; already partially acknowledged in `docs/protocol.md` §13.5; client-side mitigation obligations tracked for Phase 2).

#### NODE-05 — Info — Plaintext HTTP transport (TLS intentionally absent)

- **Severity:** Info
- **Affected component:** transport layer; `node/internal/api/middleware.go` `CanonicalHost` (line 14) and the `http://` redirect targets (`middleware.go` line 70, `handlers.go` line 415).
- **Description.** Every byte between client and node — API payloads, directory listings, the captive-portal redirect chain — rides plaintext HTTP on the open Wi-Fi. Any associated station can passively observe all traffic metadata (who syncs, when, how much, which endpoints) and the full directory; an active attacker positioned as the AP (evil twin, A6) can serve anything. This is a **normative design decision**, documented in `docs/protocol.md` §12 ("TLS is intentionally absent" — no CA will issue for `offgrid.local` on a shared static IP, and offline PKI would break the captive flow) and justified by §13: confidentiality rests entirely on the E2EE envelope, which TLS would not strengthen. The audit accepts the reasoning and records the residual exposure honestly: traffic analysis and directory harvesting by any station are possible and unprotected by design (consistent with §13.2's "Network observer" row and §13.5's traffic-analysis acceptance); NODE-04 is the one place where network-level tampering escalates beyond metadata. The `301`-based canonicalization also means browsers cache the redirect per original origin — an operator changing `CanonicalHost` would strand cached clients (operational note, not a vulnerability).
- **Recommended action:** none in the daemon (adding TLS is forbidden by the design). Keep the §13.4/§12 client-side guidance current (canonical-URL banner, E2EE, QR exchange).
- **Status:** Documented / accepted risk.

#### NODE-06 — Info — Bytes after the top-level JSON value are silently ignored

- **Severity:** Info
- **Affected component:** `node/internal/api/handlers.go` `decodeJSON` (line 424): `json.Decoder.Decode` consumes exactly one JSON value; trailing bytes after it are never read or rejected.
- **Description.** A body like `{"limit":50} garbage` parses as a valid sync request. This is harmless in this deployment: the daemon is a single HTTP/1.1 hop with no proxy in the path (no request-smuggling surface), `net/http` owns all framing, and `MaxBytesReader` caps the socket work. Enforcing strictness (read-all + re-validate, or `DisallowUnknownFields`) would buy nothing and would collide with the §15.4 unknown-member tolerance that versioning depends on.
- **Reproduction:** `curl -s -X POST http://10.42.0.1:8080/api/v1/sync -H 'Host: offgrid.local:8080' -H 'Content-Type: application/json' -d '{} trailing-garbage'` → `200 {"status":"ok",…}`.
- **Recommended action:** none; record the behavior here so it is a decision, not an accident.
- **Status:** Documented / accepted risk.

#### NODE-07 — Info — GET endpoints are unbudgeted; worst-case directory GET ≈ 1 MiB per hit

- **Severity:** Info
- **Affected component:** `node/internal/api/handlers.go` `handleGetDirectory` (line 470), `handleSync` pull path; by design per §10.1.
- **Description.** Only the two POST endpoints and the diagnostics surface carry per-IP budgets; `GET /api/v1/directory` and sync pulls are unlimited at the daemon. The worst legitimate answer is bounded — 500 directory entries × ≤2 KiB bundles ≈ 1 MiB (documented §8.1 NOTE) and pulls ≤ 200 envelopes × ≤ ~530 B — but an unbudgeted repeater can force repeated SQLite reads and large responses from a Pi-class CPU. This allocation of responsibility is deliberate and documented: §10.1 assigns read-path floods to the Track 1 shields, which answer exactly this (per-source NEW-connection hashlimit 30/min + burst 60, connlimit 32/source, CAKE 25 mbit per-host fairness, 20-station ceiling — `docs/hardening.md` §2.1).
- **Reproduction:** `while :; do curl -s -H 'Host: offgrid.local:8080' http://10.42.0.1:8080/api/v1/directory >/dev/null; done` — daemon keeps serving; airtime/CPU load bounded only by the AP-layer shields.
- **Recommended action:** none now. If a future phase ever drops the Track 1 shields from a deployment profile, revisit a small read budget mirroring `healthBudget`.
- **Status:** Already mitigated (protocol-assigned control cited: §10.1 + `docs/hardening.md` §2.1).

### 2.1 The core claims, verified end to end

The claim under audit — **"all cryptography happens in the browser; nodes and mules stay blind"** — holds in the shipped client code:

- **The SPA cannot talk to anyone but the node, and never about secrets.** The only network primitive is `xhrJSON` (`ui.js` 55–80): `XMLHttpRequest` to three fixed RELATIVE paths — `/api/v1/directory` (GET at `ui.js` 199, POST via `publishIdentity` at 912–920), `/api/v1/sync` (`ui.js` 1290) and `/api/v1/capabilities` (`ui.js` 1144). No request body ever carries private key material: the directory POST sends alias + the two PUBLIC keys + the prekey bundle's PUBLIC members and signature (`ui.js` 912–920); the sync POST sends `known_ids` (opaque id strings) and envelope wire objects holding exactly the six §3.1 ciphertext fields (`store.js` `toEnvelopeWire` 617–626, pinned field-exactly by `tests/spa_security.mjs` (e), which also asserts no secret substring appears in any wire object). There is no other egress at all: zero `fetch`/`WebSocket`/`Worker`/`importScripts`/`sendBeacon`, zero `console.*`/`alert` logging, zero `localStorage`/`sessionStorage` — asserted statically over every shipped app script by `tests/spa_security.mjs` (f).
- **Identity and prekey secrets live only in IndexedDB and only leave it through the seed-backup UX.** The identity singleton (seed, `seedB64`, `signSecret`, `boxSecret`, public keys, alias) is stored under the `identity` key of `dtn_local_store` (`store.js` 43–55, 276–284) and read back on boot (`ui.js` `initUi` 1102–1116). The prekey stock (SPK secret + unconsumed OPK secrets) lives in the additive v4 `prekeys` store (`store.js` 523–531), generated as fresh `nacl.box.keyPair()` draws — **never derived from the identity seed**, so a leaked seed opens nothing prekey-addressed (`prekeys.js` 160–185, store comment 107–120). The seed surfaces in the DOM only through the two §11-mandated backup paths: the registration backup card (`ui.js` 963) and the Identity tab's hidden textarea behind the explicit "Show seed" button (`ui.js` 612–628). This is the documented §7.3/§11 design (manual, user-triggered backup), not a leak.

### 2.2 Findings

#### SPA-01 — Low — No recorded integrity hash for the vendored crypto engine (drift was undetectable offline)

- **Severity:** Low
- **Affected component (pre-fix):** `node/web/js/vendor/nacl.min.js` and `node/web/js/vendor/qrcode.js` — the provenance markers claimed versions and refresh recipes, but no checksum was recorded anywhere in the repository (`git grep -i 'sha-256' node/web/js/vendor/` → nothing pre-fix).
- **Description.** The whole crypto engine is one vendored minified blob inside the served origin. Its markers said "tweetnacl 1.0.3, embedded verbatim — do not edit", but nothing let a maintainer or auditor DETECT a deviation without re-fetching upstream *and knowing exactly which bytes to compare*: an accidental edit, a bad copy-paste during a re-vendor, or tooling corruption of the crypto blob was invisible to the entire test suite. For the single most supply-chain-critical file in the client, that is a gap: provenance by comment is not provenance.
- **Reproduction (pre-fix):** edit any byte of the nacl embed (e.g. flip one constant) and run the full suite — every test stayed green; nothing recorded what the bytes were supposed to be.
- **Provenance verdict (the verification this finding demanded, executed during the audit):**
  - **tweetnacl: VERIFIED byte-identical to upstream.** Method: `npm pack tweetnacl@1.0.3` (registry tarball, 2026-10-06), `tar xzf`, and a byte comparison of `package/nacl-fast.min.js` against the vendored file's embedded region (bytes from the first `!function` line through the end of the minified code — the marker comments and provenance header are the only additions). Result: **identical, 32 110 bytes, SHA-256 `3ec535c004aeeb225785d8e93fb33bf99f52e399bd7dfc01969b5629baea5131`**. Sanity checks on the same blob: Curve25519 scalar clamping present at all three scalar-mult entry points (`i[0]&=248 … i[31]=127&t[31]|64`); the constant-time comparators `crypto_verify_16/32` are the branch-free `w()` routine; the PRNG setup draws from `crypto.getRandomValues` (chunked ≤ 65 536, buffer zeroed afterwards) and throws rather than falling back when absent.
  - **qrcode-generator: VERIFIED upstream + only the documented adaptations.** Method: fetched `https://unpkg.com/qrcode-generator@1.4.4/qrcode.js` (2026-10-06) and diffed. Result: the vendored file is the upstream original (SHA-256 `18ae399f81182bc9de916e9c77b195df20cc58d6f2d55a62b085a299f1bf1780`, 56 694 bytes) plus exactly the three documented adaptations — the provenance header, the leading `"use strict";` directive, and the trailing `self.qrcode` attachment block. No other byte differs.
- **Fix (in this PR):** both vendor headers now record the verified SHA-256 together with the exact offline re-verification recipe (`nacl.min.js` lines 7–14, `qrcode.js` lines 12–19), and the new `tests/spa_security.mjs` section (a) recomputes both hashes from the shipped bytes on every suite run and fails on any drift (it also undoes the qrcode adaptations in-test to prove they are the ONLY deviations, and runs the RFC 8032 §7.1 TEST 1 known-answer vector through the vendored Ed25519). A future re-vendor now MUST update the recorded hash and the test together, and an auditor can re-verify against upstream with one `npm pack` + `shasum`.
- **Regression tests:** `tests/spa_security.mjs` (a) — 14 assertions.
- **Status:** Fixed in this PR. (Phase 5's remaining supply-chain scope — the Go module — is unaffected; see the §5 row of the scope table.)

#### SPA-02 — Low — Receive path never verified the §6.2 envelope `id` (outer-field tampering invisible client-side)

- **Severity:** Low
- **Affected component (pre-fix):** `node/web/js/envelopes.js` `decryptEnvelope` (accepted any shape-valid envelope without recomputing its id) and `node/web/js/store.js` `transitRecordOf` (admitted any shape-valid envelope into the mule's `transit_queue`).
- **Description.** The client computes `id = SHA-256(canonical outer fields)` at creation (§6.2) and uses it for dedup — but never re-verified it on the receive path. Three consequences: (1) **Corruption/tamper detection gap** — the outer fields (`dest_hint`, `created_at`, `ttl`, `payload`) are plaintext and the id is a PUBLIC hash, so the id is not authentication (a knowing tamperer recomputes it); but against a tamperer who does NOT think to recompute — and against every non-adversarial corruption (a flipped byte in a store, a buggy intermediary) — the inconsistency was a free, unused detector: a re-hinted envelope (targeted re-addressing/drop), a re-dated envelope (re-aging mail past mule FIFO or node janitor eyes), a TTL-extended envelope, or a payload swap all passed silently and were processed at full trust weight. (2) **Mule-slot waste** — a shape-valid envelope with an inconsistent id occupied one of the 100 transit slots and was forwarded onward (the blind mule has no other filter — see SPA-03). (3) The §6.2 construction itself was only pinned on the SEND path and the conversion path, never as a receive-side invariant.
- **Reproduction (pre-fix):** in the loaded engine: `DTN.transitRecordOf({...env, dest_hint: "0000000000000000"}, now)` returned a full transit record (stored, carried, re-pushed); `DTN.decryptEnvelope({...env, created_at: env.created_at + 10**9}, identity, …)` proceeded to the box-open step with attacker-chosen outer metadata.
- **Fix (in this PR):** a new pure `envelopeIdMatches(env)` (`envelopes.js` 377–401) recomputes the §6.2 id over the received outer fields — creation version from `meta.orig_v` per the §15.1 id-stability rule (the same semantics `tests/version_migration.mjs` already pins for dedup) — and the receive path enforces it in exactly two places: `decryptEnvelope` rejects with the silent reason `bad_id` before any decode work (`envelopes.js` 431) and `transitRecordOf` returns null so a provably-inconsistent envelope never occupies a mule slot (`store.js` 635). No wire bytes change; every conforming sender's envelope passes by construction (ids are minted over exactly these fields); the blind v1→v2 conversion passes (§15.1 copies the id). Honest limit, stated: this is corruption/lazy-tampering detection, not authentication — a keyed adversary who recomputes the hash is still stopped only by the Poly1305 MAC and the Ed25519 signature, which is the pre-existing, correctly-layered defense.
- **Regression tests:** `tests/spa_security.mjs` (c) — 18 assertions (conforming pass, no false positive; re-hinted/re-dated/TTL-extended/payload-swapped/id-swapped rejected as `bad_id` and never stored; converted v2 passes; a faked `v:2` wrapper cannot launder a v1-minted id). The three suites whose forger fixtures re-box payloads (`crypto_roundtrip.mjs`, `chunking.mjs`, `acks.mjs`) now simulate the STRONGEST forger by recomputing the public id after tampering, so their original MAC/signature properties stay pinned — and the tampering tests double as proof that the id check does not weaken the inner layers.
- **Status:** Fixed in this PR.

#### SPA-03 — Info — Mule resources are attacker-fillable: transit-queue stuffing and unbounded `seen_ids` growth

- **Severity:** Info (real, bounded impact; protocol-inherent — the blind mule has no way to filter)
- **Affected component:** `node/web/js/store.js` `addTransitEnvelopes`/`markSeenIds`/`listSeenIds` (650–735); `node/web/js/mule.js` `evictTransitQueue` (42–58).
- **Description.** Any envelope a mule pulls that does not match its own hints is carried (`mule.js` 20–37). A hostile node a mule visits (or any station pushing through an honest node) can hand it unlimited well-formed garbage — random ciphertext boxes addressed to arbitrary 16-hex hints, ids recomputed to be consistent (SPA-02's check correctly does not and cannot stop this). Impact: (1) **cargo stuffing** — 100 garbage envelopes evict the mule's real carried cargo (FIFO by `created_at`, `mule.js` 42–58); garbage residence is bounded only by the 30-day TTL wherever it lands; (2) **`seen_ids` grows without bound** — every pulled id is recorded forever (`store.js` `markSeenIds` 715–730; no eviction exists in the store), and `known_ids` = inbox ∪ transit ∪ seen is re-sent on every sync (`ui.js` 1244–1273), so a long-lived mule's per-sync request count climbs (known_ids chunks of 500 → one POST per chunk) toward the §10.1 request budget, degrading its own syncs.
- **Reproduction:** serve a mule 50 fresh valid-shaped garbage envelopes per sync from a hostile node; the transit queue reaches 100 within two syncs (evicting real cargo) and `seen_ids` grows monotonically (observed structurally by the FIFO/garbage battery of `tests/spa_security.mjs` (d); the store growth is a direct code read — no cap on `STORE_SEEN` anywhere).
- **Why accepted:** this is the blindness trade working as specified. A mule CANNOT distinguish garbage from genuine foreign mail — opening foreign envelopes is exactly what the E2EE forbids (§13.2 mule row), and any client-side filter would break §4.3's local-only classification. Node-side admission already bounds the attacker's per-IP rate and per-node garbage mass (§8.1: 100 pushed/sync, 5000-envelope store cap, 30-day TTL). Recommended future mitigation (not applied — it changes dedup semantics): cap `seen_ids` FIFO-style (e.g. 10–20 k entries); replay exposure after eviction is benign — an id-keyed inbox `put` cannot duplicate a message, chunk parts are first-write-wins (`chunking.js` 185–200), and a re-decrypted message merely refreshes its own row.
- **Status:** Documented / accepted risk.

#### SPA-04 — Info — The node serves the client code: a modified SPA can harvest the identities of everyone who uses it

- **Severity:** Info (protocol-inherent; the audit records it precisely because it is the deployment's deepest trust assumption)
- **Affected component:** the §10.3/§12/§15.6 same-origin code-delivery design itself (every asset of `node/web/` is embedded in and served by the node).
- **Description.** The SPA is the trust root for its own crypto — and its bytes arrive from the untrusted node over plaintext HTTP (`ui.js` fixed relative paths cannot help; the origin IS the node). A malicious or compromised node can serve a doctored `index.html`/`ui.js` that exfiltrates the seed and secrets of every user who REGISTERS, IMPORTS a seed, or merely opens the app on it — no crypto in the shipped engine can defend against the engine having been replaced. This is strictly stronger than the §13.5 doctored-bundle case (which the §4.6 signature answers) and the §13.6 evil-twin row (whose "exposure is bounded client-side" holds only while the client code is genuine). The spec's implicit position is that all conforming nodes serve the byte-identical embedded binary — divergence requires a deliberately modified node — and that a user's practical code source is "any node's identical build".
- **Mitigations that exist (all verified in this phase):** the SPA requests zero external resources (CSP `default-src 'none'`, asserted by `tests/spa_structure.mjs` §2 and `tests/pwa_assets.mjs`), so code injection requires modifying the node itself, not a network position; and since SPA-01 the embedded engine bytes carry recorded SHA-256 hashes with a one-command out-of-band verification recipe — a paranoid user on any terminal can `curl` the served vendor files from a node and hash-compare against the values published in this repository, detecting a crypto-blob swap. What does NOT exist: any binding of the served code to the repository (no SRI possible same-origin, no code signature, no pinning). A real closure (signed app bundles, native app, or a verified-distribution channel) is a Phase 2/3 application-design decision (§14), out of scope for a client fix.
- **Status:** Documented / accepted risk (recommended for the Phase 3 protocol review to carry forward explicitly into the §14 native-application design).

#### SPA-05 — Info — Shared-device takeover: the unlocked browser is the identity

- **Severity:** Info
- **Affected component:** `node/web/js/store.js` (identity singleton 276–284) and the seed-display paths of `ui.js` (612–628, 963).
- **Description.** Anyone holding an unlocked browser session on a shared device gets everything: the IndexedDB `identity` row carries seed + both private keys in the clear (readable via devtools or any same-origin script — of which the closed CSP ensures there are none but the app's own), the "Show seed" button displays the backup secret on demand, and the inbox is plaintext by definition after decryption. There is no lock screen, no passphrase, no re-auth. This is the documented trust model, not a defect: §13.1 trusts exactly the sender's and recipient's own browsers; the guide's expectation box says "privacy ends at the recipient's device — protect the phone like the letter"; and §13.5 lists identity loss on data wipe as accepted. The audit records the corollary honestly: physical/share-device access is total compromise, including retrospective decryption of anything addressed to still-held prekeys-with-FS only up to the §13.5 horizon. Minor hygiene note folded in here: after a successful seed import the pasted seed lingers in the (now hidden) registration screen's textarea until the next page load — DOM-only, no network path, same trust boundary.
- **Recommended action (future, breaking):** a passphrase-encrypted identity store would bound the unlocked-browser case, at the cost of changing the seed-backup UX contract (§11) — a spec-level decision, documented only.
- **Status:** Documented / accepted risk (spec §13.1/§13.5 position).

### 3.2 Findings

#### PROTO-01 — Medium — §13.3 overclaimed hint rotation: directory-holder linkability is permanent, not epoch-confined

- **Severity:** Medium (metadata/privacy model error in the normative document; the underlying exposure is the pre-1.6 accepted risk resurfacing through an overstated mitigation)
- **Affected component:** `docs/protocol.md` §13.3 ("What the mitigation buys", residual 2) and §6.1 ("computationally independent … linkability decays"); echoed in `docs/DEVELOPMENT_PLAN.md` §1.2/§1.7 and `docs/offline-maintenance.md` §3.6.
- **Description.** §13.3 claimed: "A node operator who recomputes hint(E) for every directory user can match stored envelopes to aliases ONLY for the CURRENT epoch E … envelopes deposited in earlier epochs can no longer be attributed to an alias by recomputation." This is arithmetically wrong. The rotating derivation is `HKDF-SHA256(ikm = recipient X25519 public key, salt = epoch)` (§6.1) — the epoch is a **public counter** (it is literally the salt, published per directory entry), the ikm is the **public directory key**, and every envelope carries **`created_at` in plaintext** (§3.1), naming the deposit epoch exactly. A directory holder can therefore derive a user's hint for ANY epoch — past or future — and link every stored envelope to its alias, permanently. The candidate set is small: the hint epoch lags the deposit epoch only as far as the recipient's last republication, and sweeping candidates back over the TTL horizon (≤ 31 epochs) or further is a handful of cheap HKDF evaluations per user (`hintCandidates`, `envelopes.js` 126–140, shows the recipient itself only ever tries 2–3). What rotation genuinely buys: (a) the pre-1.6 attack (one static hash per user, computed once, valid forever) now requires per-envelope, per-epoch work — a work-factor increase, not a closure; (b) a hint alone reveals nothing, so linkage requires holding the key: envelopes deposited where the recipient's key is not yet held become linkable only after a later directory acquisition, and then only for the epochs the acquirer recomputes — rotation bounds retroactive linking after a LATE directory acquisition (the exact case §3.6 of `docs/offline-maintenance.md` widens via federation). Within a single node, where the operator holds the directory from day one, linkage is permanent — exactly the pre-1.6 accepted risk.
- **Evidence:** `docs/protocol.md` §6.1 derivation + §3.1 (`created_at` plaintext) + §10.3 (directory publishes `pubkey`, `epoch`); client candidate logic `node/web/js/envelopes.js` 126–140; §13.3's own residual 2 conceded the operator "can derive each user's hint(E) and hint(E−1)" while the binding paragraph two paragraphs above denied exactly that.
- **Fix (in this PR):** §13.3 heading, binding statement and residuals 1–2 rewritten to the honest statement; §6.1's inference sentence corrected; echoes corrected in `DEVELOPMENT_PLAN.md` §1.2/§1.7 and `offline-maintenance.md` §3.6. No wire or derivation change — the scheme itself is not broken, the documentation of its strength was.
- **Status:** Spec corrected in this PR (protocol.md 1.12.2). Documented / accepted residual (protocol-inherent: any blind-routing scheme whose hint is derivable from public data is linkable by the directory holder).

#### PROTO-02 — Low — Replay protection is live-store dedup only: captured envelopes are re-injectable after TTL eviction

- **Severity:** Low (real, bounded impact: re-delivery confusion and cap-headroom nibbling; no content exposure — MAC/signature still bind)
- **Affected component:** `docs/protocol.md` §13.5 (replay bullet); semantics in `node/internal/storage/storage.go` (`InsertEnvelopes` 582, `PullEnvelopes` 634, `DeleteExpired` 784), `node/internal/envelope/envelope.go` (Validate 190, created_at bounds 203–207), `node/internal/cleanup/cleanup.go` (15-min cadence; `main.go` 63).
- **Description.** §13.5 said replay is "harmless: mules and recipients dedup by `id`". That covers only replay against the CURRENT store. The node keeps no memory of expired ids: `INSERT OR IGNORE` (storage.go 599) dedups against live rows only; the §10.6 janitor's deletions (every 15 min, `main.go` 63) are not remembered anywhere; and §10.5 bounds `created_at` only from above (`> 0`, `≤ now + 300`, envelope.go 203–207) — there is no freshness floor. Consequently a station that captured an envelope (any station may pull the whole blind dead-drop, §13.2) can re-inject it at any later time, at any node. An injected envelope whose deadline has already passed is ADMITTED (validation passes), stored — occupying §8.1 cap headroom until the next sweep — and never served (the §10.4 inclusive boundary excludes it from the first pull); a still-unexpired capture rides again for its remaining TTL. Recipient-side absorption depends on client state that §13 did not qualify: `seen_ids` (unbounded, SPA-03) absorbs replays only for clients that keep it; a freshly initialized or seed-restored client cannot distinguish a replayed message from late mail — the text reappears in its inbox, and a replayed ack re-applies its idempotent delivery state. Prekey-addressed replay to a consumed OPK still fails the trial decrypt (the one place the model was already right).
- **Reproduction:** pull any live envelope from an open node; wait for its TTL to pass (or target another node that never saw it); re-push it verbatim. Admission answers the ordinary `200`; if unexpired, the envelope serves for its remaining TTL; a recipient that wiped its store (new browser, seed re-import) sees the old message as new mail.
- **Fix (in this PR):** §13.5's replay bullet rewritten to the honest statement (live-store-only dedup, no freshness floor, fresh-client caveat, accepted residual — a blind node cannot remember expired ids without unbounded state). No code change: the behavior is correct for a blind node; it was the documentation that claimed more than dedup delivers.
- **Regression tests:** NEW `node/internal/api/unknown_recipient_test.go` `TestExpiredEnvelopeAdmittedNeverServed` (line 202) — pins that an already-expired envelope is admitted `200` with the ordinary response shape, is stored (count = 1), is never served by a pull, and is reaped by `DeleteExpired`; together with the existing `TestPullTTLBoundaryAndDeleteExpired` (`storage_test.go` 189) and the TTL/created_at bounds rows of `TestSyncInvalidEnvelopes` (`api_test.go` 771–773) the corrected §13.5 text is fully pinned.
- **Status:** Spec corrected in this PR; behavior pinned.

#### PROTO-03 — Medium — Resource exhaustion as censorship: the store cap denies NEW mail for up to TTL_MAX, and §13 did not say so

- **Severity:** Medium (unauthenticated, service-wide denial of a community node's mailbox, bounded by TTL — real but recoverable)
- **Affected component:** `docs/protocol.md` §13.6 (store-flooding row, and the absence of any mule-resource row); enforcement in `node/internal/api/ratelimit.go` (budgets) + `storage.go` (cap, reject-newest).
- **Description.** §13.6 presented the 5000-envelope cap as the defense against store flooding. The cap is equally the attack surface: a single hostile station acting entirely within the per-IP envelope budget (burst 600, refill 600/hour) can deposit 5000 junk envelopes with `ttl = 2592000` in under eight hours (600 burst + 4400 at 600/h); from then on every push — including all legitimate mail — answers `429 node_full` until the junk expires through its OWN ttl, i.e. up to 30 days per injected batch, repeatable to sustain, scaling linearly with collusion. The pre-audit text (and `docs/hardening.md` §3's "the global cap plus the TTL janitor win that race by design") is accurate only for short-TTL junk: the janitor wins no race against attacker-chosen TTL_MAX. The keep-oldest policy is the genuine mitigation — mail already deposited stays servable; what a fill denies is NEW mail. The same blindness applies to mule resources, which §13 did not mention at all: a hostile node can fill a visiting mule's 100-slot transit FIFO with valid-shaped garbage (evicting real cargo, `mule.js` 42–58) and grow `seen_ids` without bound (SPA-03) — carried-mail loss indistinguishable from ordinary DTN loss. Blindness is why no conforming build can close this: a node that preferred "legitimate" mail would have to judge content.
- **Evidence:** budgets `ratelimit.go` (`syncEnvelopeBurst`, refill 600/h); cap + reject-newest `storage.go` 107–125, 582–599; cap-holds-under-flood pinned by `TestFloodJunkEnvelopesStoreCapHolds` (`flood_test.go`); mule FIFO `mule.js` 42–58, stuffing analysis SPA-03.
- **Fix (in this PR):** §13.6 gains the "Resource exhaustion as censorship" statement with the honest TTL_MAX bound, the mule-stuffing residual, and the keep-oldest caveat. No code or limit change — inherent to the shared finite store.
- **Status:** Spec corrected in this PR (protocol.md 1.12.2). Documented / accepted residual.

#### PROTO-04 — Info — §13.6's evil-twin row ignored that the node serves the client code

- **Severity:** Info (protocol-inherent; the deepest trust assumption, already recorded as SPA-04)
- **Affected component:** `docs/protocol.md` §13.6 (evil-twin row) + §12 (same-origin).
- **Description.** The row claimed "client-side crypto bounds the exposure" against an evil twin. True only while the client CODE is genuine — and the code is served by the very node under attack over the same origin (§12): an evil twin can serve a modified SPA that harvests the seed and secrets of every user who registers, imports a seed, or unlocks on it (SPA-04). E2EE bounds nothing in that case; the "cannot read / cannot forge" rows hold for envelopes, not for the identity creation flow. Practical mitigations are operational: since SPA-01 the served crypto embeds carry recorded SHA-256 hashes with an offline re-verification recipe (an engine swap is detectable from any terminal), and the structural closure (signed/native distribution) is reserved for §14. The wildcard-DNS + canonical-origin convenience that makes mule storage portable (§12) is the same mechanism that makes the fake node indistinguishable from a genuine one before code verification.
- **Fix (in this PR):** the §13.6 evil-twin row now conditions its claim on the client code being genuine and points at the new §13.5 "the node serves the client code" bullet (with the engine-hash check). No code change.
- **Status:** Spec corrected in this PR. Documented / accepted residual (cross-ref SPA-04).

#### PROTO-05 — Low — QR-pinned encryption keys defer silently to the node directory (NODE-04's reach includes QR-verified contacts)

- **Severity:** Low (a mitigation channel weaker than a design record promises; requires the NODE-04 tamper to be present)
- **Affected component:** `node/web/js/qr.js` `qrMergeRecipients` (237–281: the directory's `x25519` at 250 wins; a merged contact keeps only its alias, 262–265); `docs/protocol.md` §4.7 merge rule + trust model; contradiction in `docs/offline-maintenance.md` §3.5.
- **Description.** This resolves the open question NODE-04 left to Phase 2: the §4.7 merged picker lets the DIRECTORY supply `x25519`/`epoch`/`prekeys` for any entry that exists — including for a QR-pinned contact (only the display alias is kept from the contact). Since x25519 is seed-derived and permanent, an honest directory and an honest QR always agree; a divergence is therefore by construction the NODE-04 tamper signal (a hijacked entry carrying the attacker's x25519 under the victim's pubkey) — and the shipped client resolves it SILENTLY in the directory's favor. The QR exchange thus authenticates the Ed25519 identity binding, but the encryption path travelled through a directory can still be redirected to the attacker even for contacts verified in person; the QR's `x` is used only when the directory lacks the entry. `docs/offline-maintenance.md` §3.5 specifies the opposite behavior for the federation work ("QR-scanned or pasted contacts keep their keys … NEVER overwritten"; warn on divergence) — a documented-vs-implemented contradiction this phase reconciles on paper: §3.5 is future-work design intent, §4.7's directory-wins rule is the shipped contract, and the §13.5 residual now says so.
- **Reproduction:** register a contact pair via §4.7 QR exchange; hijack the victim's directory entry per NODE-04's reproduction (republish the victim's `pubkey` with an attacker `x25519`); the sender — holding the QR-pinned contact — still encrypts to the attacker's key, with no warning.
- **Fix (in this PR):** documentation, not behavior: §4.7's trust model states the precedence and its consequence; a new §13.5 bullet records the silent-divergence resolution and points at the pin-and-warn refinement. Changing the merge rule would alter the §4.7 contract and is deferred to the workstream that already owns the warning design (`offline-maintenance.md` §3.5 / follow-up issue 7).
- **Regression tests:** `tests/qr_identity.mjs` (e) extended (lines 347–363): a directory entry whose `x25519` diverges from a QR-pinned contact's `x` resolves to the DIRECTORY value — pinning the shipped precedence so the future pin-and-warn change must consciously update this test.
- **Status:** Spec corrected in this PR; behavior change deferred (documented).

#### PROTO-06 — Medium — §13.5 understated the directory-entry swap's actor set: any station, not just the node

- **Severity:** Medium (same class as NODE-04, whose Phase 1 nuance this spec text now records)
- **Affected component:** `docs/protocol.md` §13.5 (doctored-bundles bullet); mechanism in `handlers.go` `handlePostDirectory` (592) — unauthenticated by §10.3 design.
- **Description.** §13.5 said "the signature does NOT close the pre-existing hole that the NODE can swap any entry's `x25519` member". ### 4.1 The island claims, verified end to end

- **Client isolation (the issue's headline question) — ENFORCED, in three independent layers, all pinned.** Layer 1, L2: `ap_isolate=1` (`hostapd.conf` 63) — every frame a client emits goes to the AP and to nothing else. Layer 2, L3: the FORWARD chain has policy DROP, ZERO accept rules, and a redundant blanket `-s 10.42.0.0/24 -j DROP` plus `-d 10.42.0.0/24 -j DROP` stating the invariant twice over (`iptables.sh` 384–412); `tests/hardening_structure.sh` §4 counts the accepts (0), proves every FORWARD rule is subnet-scoped, and §2 pins `ap_isolate=1` itself. Layer 3, identity: no `bridge=` line exists (a bridge would leak L2 frames to any wired network; `hostapd.conf` 20–23, pinned at `hardening_structure.sh` §2) and `/etc/network/interfaces` configures ONLY `lo` + `wlan0` (an Ethernet cable gives an attacker no bridge into the AP — `provision.sh` 245–253). The provisioned operator checklist closes the loop on real hardware: "two clients cannot reach each other (isolation): ping from client A to client B must fail" (`provision.sh` final_report step 4).
- **Wildcard DNS is the node's ENTIRE DNS answer surface, by construction.** `address=/#/10.42.0.1` (`dnsmasq.conf` 80) plus `no-resolv` and zero `server=` lines (pinned, §3 of the structure suite): every A query gets four bytes pointing back at the node, every other record type gets NXDOMAIN/NODATA, and there is no upstream to tunnel through. The only interceptable content is what the node itself serves (below). The `dhcp-authoritative` mode is sound here: there is exactly one DHCP server on the island, and the flag only skips the RFC 2131 collision wait (`dnsmasq.conf` 89–92).
- **The captive-portal redirect chain cannot leave the node.** The nat hook REDIRECTs tcp/80 → 8080 on `wlan0` ONLY (`iptables.sh` 280–281) — REDIRECT, not DNAT, so nothing is ever sent elsewhere — and the nat table contains zero MASQUERADE/SNAT rules (pinned): the node cannot be turned into a router. Upstream, the Go daemon answers the OS probes with a 302 to the CONSTANT canonical origin and canonicalizes Host mismatches with a 301 to the constant origin + request URI — verified end-to-end in Phase 1 (§1.3 item 6: no open redirect, no host reflection, no header injection; pinned by `TestCanonicalHostRedirect`, `TestCaptiveProbesExemptFromCanonicalRedirect`, sync_e2e §7). Wildcard DNS therefore lands stations on the node and the node points them only at itself. There is no nginx/apache in the stack (packages installed by provisioning: hostapd, dnsmasq, iptables, iw, dnsutils, curl — `provision.sh` 188–192): the Go binary IS the only web server.
- **L4 rate limiting is real and per-source:** DNS hashlimit 25/s (burst 50) per source on udp+tcp/53 BEFORE the accepts, portal NEW-connection hashlimit 30/min (burst 60) + connlimit 32/source on 8080, ICMP 5/s + fragmented-ICMP dropped outright, with the thresholds' legitimate-budget math documented in the generator header (`iptables.sh` 106–123) and every rule pinned by the structure suite §4. The documented INPUT-ACCEPT stance is deliberate and on record (`iptables.sh` 300–309): the externally reachable services are exactly the accepts, and client egress dies in FORWARD regardless — but see PI-01 for the IPv6 hole in that reasoning.
- **SSH hardening is shipped, validated-before-install, and default-dropped from the AP.** Keys only, no root login, no agent/TCP forwarding, tight auth budgets (`sshd-hardening.conf` 19–26); `harden-ssh.sh` runs `sshd -t` against the merged parse-order configuration BEFORE touching anything (97–114) and re-greps the two non-negotiables after install (154–155); the firewall drops client tcp/22 unless the operator explicitly passes `ALLOW_SSH=1` (`iptables.sh` 352–365, both stances pinned by the structure suite §9b). No script creates or mutates a loginable user: the daemon account is `useradd --system … --shell /usr/sbin/nologin` (`provision.sh` 421) with a locked-password repair path (`harden-services.sh` 166–169) — no default credentials anywhere in the provisioning. Residuals: PI-04.
- **Unattended security updates are enabled, feature updates are not.** `harden-upgrades.sh` writes a deterministic security-only override (`#clear Origins-Pattern` → Debian security pool + `archive.raspberrypi.com`, because the Pi's firmware/kernel/hostapd live there), forbids automatic reboots (the operator owns the reboot), and never touches the daemon itself (not an apt package — updates are the manual `install.sh` path). Pinned §9e.
- **systemd hardening is the full set on the exposed daemon and good on the helpers.** `dtn-node.service`: unprivileged `User=dtn`, `NoNewPrivileges`, `ProtectSystem=strict` with `ReadWritePaths=/var/lib/dtn-node` as the ONLY writable path, `PrivateTmp`, `ProtectKernelTunables/ControlGroups`, `RestrictAddressFamilies` (the four AFs the runtime needs), `MemoryMax=192M`, `RestrictSUIDSGID`, `MemoryDenyWriteExecute` (safe because the build is cgo-free — the claim is documented in the unit and re-checkable in `build.sh`), `Type=notify` + `WatchdogSec` + `Restart=always/RestartSec=5`. Every helper unit (both shields, watchdog, telemetry) runs with `NoNewPrivileges` + `ProtectSystem=strict` + `ReadWritePaths=/dev/shm` only — their state lives and dies in tmpfs. All pinned §8/§9c/§9i. The tighter extras NOT shipped (`CapabilityBoundingSet=`, `SystemCallFilter=`) are noted as future hardening, deliberately not retrofitted mid-audit.
- **The provisioning scripts have no injection surface.** `COUNTRY` is regex-gated `^[A-Z]{2}$` before the sed splice into hostapd.conf (`provision.sh` 153–155); `ALLOW_SSH` is compared literally; there is no `eval` anywhere under `raspberry/`; the `STEPS` subset selector is a case-whitelist over exactly the ten function names (`provision.sh` 574–581); every config file is written from fixed heredocs via `mktemp` + `install_file` (compare-before-replace, `.dtn-bak` backup). `install.sh` option values reach only curl URLs and literal comparisons. The one root-code-execution decision an operator makes is WHERE the provisioning tree comes from — which is precisely the supply-chain question of §5 (SUPPLY-01/02/03).

### 4.2 Findings

#### PI-01 — Medium — IPv6 is unaddressed by the island: a live link-local address is a side door around every Track-1 per-source shield

- **Severity:** Medium (an unauthenticated associated station can shed every per-source L4 limit; impact is bounded by the daemon's own budgets and the radio, and fully recoverable — but the entire anti-circumvention layer silently assumed IPv4)
- **Affected component (pre-fix):** `raspberry/firewall/iptables.sh` (iptables — IPv4 — only; zero `ip6tables` rules), `raspberry/provision.sh` (nothing disabled IPv6; repo-wide grep for ipv6/ip6tables over `raspberry/`, `tests/`, `docs/hardening.md` returned ZERO hits pre-fix).
- **Description.** Raspberry Pi OS leaves IPv6 enabled by default, so `wlan0` auto-configures a link-local address (`fe80::/10`) as soon as it comes up — the ifupdown static stanza configures only the IPv4 address. Nothing on the island serves IPv6 ON PURPOSE (the canonical origin is 10.42.0.1, protocol §12), but "nothing serves it" is not "nothing listens": the daemon binds `-addr :8080` — a wildcard, dual-stack socket (`main.go` 169) — and dnsmasq binds `wlan0`'s addresses (`bind-interfaces`, `dnsmasq.conf` 21). An associated station can discover the node's link-local in one multicast (`ping6 ff02::1`) and then connect to `[fe80::…]:8080` or query DNS at its v6 address — and NONE of the Track-1 shields exist on that path: the DTN_INPUT jump, both DNS hashlimits, the portal SYN hashlimit, the connlimit and the DTN_DNSBL shed chain are all iptables (v4) rules (`iptables.sh` 296–367); the dns-shield's parser recognizes only dotted-quad sources (`dns-shield.sh` 120), so a v6 flooder is invisible to it too; the station-shield correlates by DHCP lease (v4 only). The attacker sheds 25 q/s DNS caps, 30/min portal handshakes, 32-connection caps and every blacklist entry, exactly the resource-exhaustion the shields exist to prevent (A1/A3) — against `dnsmasq` (single-threaded) and the daemon's unbudgeted GET surface (NODE-07). What still holds: ap_isolate (L2), FORWARD isolation (no v6 forwarding is configured and none is needed), the daemon's own per-IP budgets (keyed on `RemoteAddr`, family-agnostic, `ratelimit.go` 208) and its timeouts (NODE-02). This is the one finding where the documented INPUT-ACCEPT stance (`iptables.sh` 300–309, "attack surface equals the services we run") was silently wrong: over v6 the attack surface equaled "everything that listens".
- **Reproduction (pre-fix):** from an associated station: `ping6 -c2 ff02::1%wlan0` → the node answers with its link-local; `curl -g 'http://[fe80::1%wlan0]:8080/api/v1/directory'` (or the EUI-64 address) → the portal answers, with no hashlimit, no connlimit, no DNSBL ever consulted. A flood loop from that address trips no shield at any layer.
- **Fix (in this PR):** IPv6 is disabled on every client-facing interface by provisioning (`provision.sh`, `static_ip` step): a new `/etc/sysctl.d/99-dtn-island.conf` sets `net.ipv6.conf.{default,wlan0,eth0}.disable_ipv6 = 1`, applied immediately via `sysctl -p` (missing-interface errors tolerated — the file loads again at the activating reboot). No v6 address on `wlan0`/`eth0` → no v6 socket to connect to, no v6 DNS to query: the class is closed at the interface instead of mirrored rule-by-rule (an ip6tables mirror would have re-implemented every shield for a protocol the island deliberately does not speak). Loopback keeps its IPv6 (`conf.all` deliberately NOT set) so the daemon's dual-stack wildcard bind and the 127.0.0.1 health probes stay exactly as they were. `default=1` covers interfaces created after provisioning. The static_ip step runs in the upgrade STEPS subset too, so already-provisioned nodes receive the file on their next `install.sh --upgrade`.
- **Regression tests:** `tests/hardening_structure.sh` §3b — 6 new assertions (file installed at the exact path; all three directives present line-exact; `conf.all` hammer absent; apply command present).
- **Status:** Fixed in this PR.

#### PI-02 — Low — Per-source L4 shields key on attacker-chosen identities (source-IP rotation, DHCP pool pressure)

- **Severity:** Low (real but bounded: the shields' granularity is finer than the adversary's control, and the binding identities — association + station MAC — still enforce)
- **Affected component:** `raspberry/firewall/iptables.sh` (hashlimit `--hashlimit-mode srcip`, connlimit `--connlimit-mask 32`); `raspberry/dnsmasq/dnsmasq.conf` (201-address pool, no per-client lease cap).
- **Description.** On an open AP the node does not bind IPs to stations: a single associated station can emit packets with arbitrary source IPs, and each fresh IP mints a fresh hashlimit bucket and its own connlimit allowance — the per-SOURCE shields rotate as fast as the attacker does. Likewise the 201-lease DHCP pool has no per-client cap (dnsmasq has no native one); pressure is bounded only by `max_num_sta=20` (one association ≈ one lease per real MAC), and a station can additionally squat any of the 250 static IPs unauthenticated. What keeps all of this small: (a) the radio is the real bottleneck (cake per-host fairness caps the abuser's airtime); (b) the identities the attacker CANNOT rotate — the 802.11 station MAC behind `hostapd_cli all_sta` counters and the association ceiling — are exactly what `dtn-station-shield.sh` enforces (64 MiB/association quota, 64-connection cap, per-MAC deauth with cooldown); (c) impact is self-degrading and fully reversible (12 h leases, counters reset on reassociation). The honest statement: L3/L4 per-source fairness on an open L2 is best-effort by nature; closing it fully means MAC-binding firewall enforcement (ebtables-class machinery) — a new layer, documented here as future hardening, deliberately not built mid-audit.
- **Status:** Documented / accepted risk (mitigations that bind: `max_num_sta=20` + station-shield per-MAC deauth, both pinned).

#### PI-03 — Info — Data at rest: an extracted SD card yields the plaintext directory and all ciphertext envelopes

- **Severity:** Info (consistent with the documented blind-node trust model; recorded so it is a decision, not an accident)
- **Affected component:** `/var/lib/dtn-node/node_storage.db` (SQLite, WAL) — directory table plaintext: `alias` ↔ ed25519 `pubkey` ↔ `x25519` ↔ `epoch` ↔ prekey bundles; envelopes table: opaque ciphertext.
- **Description.** Whoever holds the card (or any local root) reads the whole store: the directory in the clear — the same dataset §13.2 already grants the node operator — and every envelope, which is ciphertext that §13.2 already lets anyone pull off the air. There is no at-rest encryption and this audit does not propose one: the node's threat model treats node-holder and operator as the same trust level, there is no key-management story that would not break the offline/unattended design, and nothing CLIENT-secret ever exists on the node to steal (seeds/private keys never leave the clients — Phase 2 §2.1). What the deployment already does for physical tamper resistance: the optional read-only root with tmpfs upper (staged default-OFF, operator opt-in — `enable-readonly-root.sh`, header note in `provision.sh` 60–66), the volatile journald, and shield/telemetry state that lives only in tmpfs so no MAC/IP survives extraction or reboot (all pinned §9d/§9f–§9h).
- **Status:** Documented / accepted risk (spec §13.2 position; Phase 3's verdict table row 2).

#### PI-04 — Info — SSH hardening is conditional on sshd existing; image-level users are outside the scripts' reach

- **Severity:** Info
- **Affected component:** `raspberry/harden-ssh.sh` 82–85 (no `sshd` binary → "no SSH attack surface, nothing to do", exit 0); `raspberry/provision.sh` 488–493 (drop-in verify skipped when sshd absent); no script audits or rotates OS-level user passwords.
- **Description.** Two conditionalities, both documented on the scripts but worth the audit's record. (1) The keys-only drop-in is installed only when `openssh-server` is present — on an sshd-less image there is no listener to harden, which is correct; the provision-time verify mirrors the condition. (2) No provisioning script creates loginable users, but it also cannot remodel the IMAGE's users: an operator flashing an old image that still carries a default-password account (the pre-2022 `pi`/`raspberry`) brings that account themselves. The network exposure is closed regardless — client tcp/22 is firewall-dropped by default (`track3:ssh-never-reachable-from-clients`), and where sshd exists `PasswordAuthentication no` kills password auth for ANY user — leaving the physical serial/console path, which is the documented field-ops recovery channel (`harden-ssh.sh` header, LOCKOUT NOTE; the power snippet keeps the PL011 UART available for exactly that). Operator duty (already in the script headers): flash a current image, install the operator key and verify a key-based login before walking away when `ALLOW_SSH=1`.
- **Status:** Documented (mitigations shipped and pinned: §9a/§9b of the structure suite).

### 4.3 Checklist coverage — what was verified as OK

1. **hostapd surface** — open-by-design explicit (`wpa=0`, `auth_algs=1`, no `wpa_passphrase` anywhere); WPS entirely absent (`wps_state`/`wps_pbc`/`eap_server` appear nowhere — a virtual push-button on an open AP would have been absurd; NOW PINNED so it stays that way); SSID broadcast on (`ignore_broadcast_ssid=0` — hidden SSIDs break captive detection and add zero security); `max_num_sta=20` association ceiling documented as the L2 backstop of the whole shield stack; `ctrl_interface` in a root-owned directory, local UNIX socket only.
2. **dnsmasq surface** — bound to wlan0 only (`interface=` + `bind-interfaces`, so nothing answers on lo/eth0); the wildcard is the only answer; probe domains deliberately NOT carved out (pinned); DHCP options 3/6 point everything at the node; lease file pinned (the station-shield's correlation source, read-only).
3. **iptables ruleset** — the FORWARD invariant is stated three ways on purpose (policy DROP, the named escape-route kills with per-rule counters for operator forensics, the blanket subnet drops); REDIRECT (not DNAT) keeps every captive connection local; zero NAT egress anywhere (pinned) — a rogue-router role is structurally impossible; client egress dies in FORWARD even if an uplink interface ever appears; the INPUT-ACCEPT stance is documented with its rationale (and its v6 blind spot is now fixed, PI-01).
4. **L4 rate limiting** — present, per-source, documented thresholds with legitimate-budget math (§4.1); applies BEFORE the accepts (the UDP-ESTABLISHED bypass is deliberately closed — no ctstate qualifier on the DNS limits).
5. **systemd** — full hardening set on the exposed daemon; tmpfs-only writable surface on every helper; restart policies everywhere (`Restart=always` on the daemon, `RemainAfterExit` oneshots for boot-state, timers as the activation surface); boot order encoded in unit dependencies (firewall Before the daemon, shaping before hostapd).
6. **install.sh integrity mechanics** — offline bundle completeness checked before anything runs (binary + SHA256SUMS + tarball); both assets checksum-verified fail-closed since this phase (SUPPLY-01); extraction into a `mktemp` sandbox with an EXIT cleanup trap; only TMP is ever deleted (never a user checkout); the upgrade path refuses never-provisioned boxes (require_provisioned_node) and binds the stop→backup→swap→gate→rollback order (pinned + live-tested, `tests/upgrade_e2e.sh`).
7. **upgrade.sh mechanics** — backup-before-touch with generationed prune (keep 3), binary_sha256 recorded per generation (an offline verification hook, cited in §5.1), health gate compares the SERVING build identity against the STAGED binary's self-reported identity, automatic rollback re-verifies health against the OLD expectations and keeps the displaced store as evidence. All of it live-tested rootlessly by `tests/upgrade_e2e.sh` (70 assertions at this revision).

### 5.1 The supply-chain claims, verified end to end

- **The Go module inventory is minimal and explicable — every dependency has a stated role.** Two direct requirements: `modernc.org/sqlite v1.60.1` (pure-Go SQLite — the single supply-chain-critical dependency, chosen so `CGO_ENABLED=0` builds stay fully static; the alternative is not stdlib but a bespoke storage engine, so the dependency is irreducible) and `golang.org/x/sys v0.48.0` (syscall plumbing for sdnotify/power). Eight indirect requirements, all from the sqlite/libc family (`modernc.org/libc`, `mathutil`, `memory`, `go-humanize`, `go-isatty`, `google/uuid`, `ncruces/go-strftime`, `bigfft`). No `replace`, no `exclude` directives; `go 1.26.0` toolchain pin; 26 modules in the build list; `go.sum` is complete and `go mod verify` reports all modules verified — the entries beyond go.mod's list are the module-graph hashes pruned-mode bookkeeping requires, not fetched code.
- **Freshness: both direct dependencies are CURRENT.** `go list -m -u modernc.org/sqlite golang.org/x/sys` against the module proxy (2026-10-06) reports no available updates for either. No `GOFLAGS`/`GONOSUMDB`/`GOPRIVATE`/`GOINSECURE`/`GONOSUMCHECK` appears anywhere in `raspberry/`, the `Makefile`, `.github/workflows/` or `docs/BUILD.md` — checksum-database verification is at its defaults (ON) for every module fetch at build time.
- **No vendoring — and the build does not need it to be trustworthy.** Reproducibility rests on the locked `go.mod`/`go.sum` plus the sumdb, not on a vendored copy: `build.sh` builds with `-trimpath`, `CGO_ENABLED=0`, pinned `GOARM` (6/7) per target and a build identifier stamped `-X main.build=$(git describe --always --dirty)` — the `--dirty` suffix is deliberate supply-chain signal (a dirty-tree build identifies ITSELF as such via `GET /api/v1/health`, and `upgrade_node`'s health gate refuses an identity mismatch). Same commit + same toolchain → byte-identical binaries; toolchain patch drift is the one variance, bounded by the `go 1.26.0` directive (GOTOOLCHAIN resolves it exactly). The embedded SPA rides `go:embed` of `web/` — same input tree, same binary; the committed icon PNGs are reproducible by design (`tools/gen_icons.mjs`: pure integer/fixed-palette math, deterministic CRC-32, zlib level 9, NO timestamp chunks in the hand-rolled PNG encoder — and git pins the committed bytes, `tests/pwa_assets.mjs` pins structure/dimensions).
- **The release workflow (READ-ONLY review) is lean and self-contained.** Tag-push triggered only; `actions/checkout@v4` + `actions/setup-go@v5` (the ONLY two third-party actions, both tag-pinned — noted, not changed: SHA-pinning is the stronger practice); `go-version-file: node/go.mod` so CI builds with the same toolchain the repo pins; the binaries come from the repo's own `build.sh`; `raspberry-<tag>.tar.gz` is packaged from the same commit; `SHA256SUMS` is generated IN CI over all five assets (three binaries + the provisioning tree + DEPLOY.md). No caching, no build scripts from outside the repo.
- **A field operator CAN verify a deployed binary — the recipe exists at every stage.** At install: `install.sh` verifies the binary AND the provisioning tarball against the release `SHA256SUMS` (SUPPLY-01, below). Post-activation: `GET /api/v1/health` exposes the `build` member — the git-describe identity of the RUNNING binary, comparable with the release tag (this is exactly what `upgrade_node`'s gate automates). Offline: each backup generation's `MANIFEST.txt` records `binary_sha256`, so `sha256sum /opt/dtn-node/dtn-node` against the release sums (or the manifest) verifies any node from any trusted terminal.
- **The committed-binaries question RESOLVED: they are not committed.** `node/dtn-node-linux-arm64|-armv7|-armv6` are gitignored from the start (`.gitignore` 5–9, matching `build.sh`'s "Outputs (all gitignored)" contract); `git ls-files` counts ZERO of them and no commit on any reachable branch ever carried one — the "stale duplicate of a release artifact sitting in the repo" hazard from the issue checklist does NOT exist, and no removal question arises (removal would break the documented local-checkout install path). What DOES exist is the local-tree hazard of SUPPLY-03.
- **Vendored JS provenance — cited, not redone:** SPA-01 (Phase 2) verified tweetnacl 1.0.3 and qrcode-generator 1.4.4 byte-identical to upstream (plus the three documented adaptations), recorded both SHA-256s in the vendor headers, and pinned them with the recompute-on-every-run test `tests/spa_security.mjs` (a). That chain is unaffected by anything in this phase.

### 5.2 Findings

#### SUPPLY-01 — Low — install.sh ran the provisioning tarball WITHOUT checksum verification (only the daemon binary was verified)

- **Severity:** Low (the verified binary and the unverified tree came from the same release over the same channel, so exploitation required the channel compromise that SUPPLY-02 already covers — but the gap made the existing check misleading: root-executed code was held to a weaker standard than the data it launches)
- **Affected component (pre-fix):** `raspberry/install.sh` — the checksum block verified `dtn-node-linux-$BINARCH` only; `raspberry-<tag>.tar.gz` (which carries `provision.sh` and every config that runs as root) was extracted unchecked, online AND offline. `docs/BUILD.md` (329) meanwhile claimed the offline path was "checksum-verified too".
- **Description.** The release `SHA256SUMS` covers five assets (release.yml 71–75), but the installer consulted it for exactly one. An operator who hand-inspects a USB bundle (the offline workflow exists precisely because the channel is distrusted) got a false guarantee: the binary's hash was checked, the root-running provisioning tree's was not — a corrupted/spoofed tarball on the stick provisioned whatever it carried. The failure was one of degree, not of kind (SUPPLY-02: the sums file itself is unsigned), but it also made the shipped documentation wrong.
- **Fix (in this PR):** a fail-closed `verify_sum` helper now verifies EVERY asset the installer USES, before any of it runs, on BOTH paths: the binary and the tarball (matched by exact last-field or exact `/name` suffix in `SHA256SUMS` — a substring of another asset's name cannot verify; proven: `dtn-node-linux-arm` does not match the arm64/armv6 lines); mismatch or missing entry aborts with no side effects (the tarball is extracted only after both hashes pass — the verification→extraction order is itself pinned). The `--offline` path resolves the bundle's actual tarball name and checks it the same way. The two BUILD.md claims are now true.
- **Verification (executed during the audit, not just pinned):** the real `verify_sum` was exercised standalone — honest sums → `checksum OK` for both assets; a one-byte-tampered tarball → dies `checksum mismatch for raspberry-v9.9.9.tar.gz (expected …, got …)` exit 1; an unlisted name → dies `no checksum for … exit 1`.
- **Regression tests:** `tests/upgrade_e2e.sh` §0 — 4 new assertions (verification order define→binary→tarball→extract; both `die` paths present; exact-field matcher present; the SUPPLY-03 warning count).
- **Status:** Fixed in this PR.

#### SUPPLY-02 — Low — the release channel has no signature: SHA256SUMS rides the same channel as the artifacts it pins

- **Severity:** Low (hash-pinning defeats corruption, truncation, wrong-tag mistakes and stale caches; it does NOT defeat an attacker who controls the channel itself — repo takeover, a malicious release edit, or a compromise of the TLS origin lets the attacker regenerate SHA256SUMS in the same stroke. The `curl | sudo bash` Path 1 adds a script/artifact drift window: install.sh comes from MOVING `main`, the assets from the latest tag)
- **Affected component:** `.github/workflows/release.yml` (publishes unsigned SHA256SUMS), `raspberry/install.sh` (fetches sums and artifacts from the same `BASE`).
- **Description.** This is the classic unauthenticated-mirror gap, stated here as an accepted residual WITH its designed closure on record: `docs/offline-maintenance.md` §2.1–§2.2 specifies the signed release capsule — an Ed25519 detached signature over `metadata ‖ payload` generated by `capsuletool`, the private key living on an air-gapped machine with a two-copy USB ceremony, `release_key.pub` shipped in the release bundle so a kit-provisioned node pins it during the checksum-verified install, plus staging, apply policy and anti-rollback counters (§2.4–§2.6). That document is an explicit DESIGN RECORD — complete and implementable, NON-NORMATIVE until its follow-up issues land — and none of it is implemented today (`node/internal/capsule` does not exist). The audit's position: the residual is acceptable for the current threat model (an attacker able to rewrite the GitHub release can also rewrite `main`'s installer and every doc that names the URLs — the channel, not the hash, is the trust root), but it is the single highest-value pending hardening in the repo and its unimplemented status should not be lost. Interim operator guidance (documented in BUILD.md flows): prefer `--ref vX.Y.Z` over latest-resolve, and treat the offline USB bundle as the verification boundary — copy it from a trusted terminal and keep the SHA256SUMS with it.
- **Status:** Documented / accepted risk; designed fix cited (offline-maintenance.md §2, unimplemented).

#### SUPPLY-03 — Low — the local-checkout install path deploys an unverified, possibly stale binary without warning

- **Severity:** Low (developer-intended path, but it provisions root services from whatever binary happens to sit in the tree)
- **Affected component (pre-fix):** `raspberry/install.sh` LOCAL_TREE branch — "local checkout with a prebuilt binary detected: nothing to download", then `provision.sh` `install_binary` (`provision.sh` 433–441) installs it with zero verification and zero provenance output.
- **Description.** The audit checkout itself demonstrates the hazard: its `node/dtn-node-linux-*` binaries were built 2026-10-04, two days before the current `main` tip — running `sudo ./install.sh --country AR` from this tree would have provisioned a stale daemon with no signal that anything was off. The upgrade mode catches identity drift at its health gate; a FRESH install has no gate, and the first human-readable identity check would be an operator's manual `GET /api/v1/health`. The committed-binary variant of this hazard was refuted (§5.1 — nothing is in git); this is its local-tree shadow.
- **Fix (in this PR):** the LOCAL_TREE branch now logs two explicit WARNINGs before proceeding: the local binary is installed AS IS with no SHA256SUMS to verify it against, and the operator should confirm it is a current `node/build.sh` output and check the build identity via `GET /api/v1/health` after activation. A fuller closure (refusing dirty trees, embedding an expected identity) would redesign the documented dev path — noted, not applied.
- **Regression tests:** `tests/upgrade_e2e.sh` §0 pins the warning pair (the same assertion block as SUPPLY-01's).
- **Status:** Fixed in this PR.

#### SUPPLY-04 — Info — Go module hygiene dossier (the §1.4 item 9 deep dive, closed)

- **Severity:** Info
- **Affected component:** `node/go.mod`, `node/go.sum`.
- **Description.** The full dossier is §5.1: minimal direct set (sqlite + x/sys, both irreducible and both CURRENT per the proxy on 2026-10-06), indirect set confined to the sqlite/libc and golang.org/x families, complete go.sum with sumdb verification at defaults, no replace/exclude, no env tampering, toolchain pinned. - **Status:** Documented.

#### SUPPLY-05 — Info — release workflow observations (reviewed READ-ONLY)

- **Severity:** Info
- **Affected component:** `.github/workflows/release.yml` (out of bounds for edits per the repo rule — reviewed only).
- **Description.** Sound: tag-push trigger; CI-generated SHA256SUMS over ALL five published assets; the provisioning tarball is cut from the same commit as the binaries; only two third-party actions, both mainstream; builds via the repo's own `build.sh` with the repo-pinned toolchain. Noted, not changed: the two actions are tag-pinned rather than SHA-pinned (the weaker pin — a compromised action tag could run in this workflow's `contents: write` context; SHA-pinning is a one-line hardening for the maintainers to consider); the workflow has no `concurrency` guard (a re-tag race is theoretically possible; `gh release upload --clobber` makes the outcome replace-in-place rather than corrupt). - **Status:** Documented.
