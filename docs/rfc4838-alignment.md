## 1. Executive summary

To what extent is Offgrid "a DTN system" per RFC 4838? **At the architecture level: genuinely and almost completely. At the protocol level: not at all, and deliberately not.** RFC 4838 defines an *architecture*, not a wire format: store-and-forward of complete messages ("bundles") over persistent storage inside the network, endpoints named independently of topology, self-declared message lifetimes, and delivery over intermittently connected paths. Offgrid implements all of those load-bearing ideas: an encrypted message is an atomic envelope (protocol.md §3) that sits in SQLite dead-drops (§9) and mule `IndexedDB` queues (§11) until a human walks it to the next node; every envelope carries a sender-stamped creation time and TTL that the network enforces blindly (§10.4/§10.6); addressing is a key-derived hint that is never bound to a location (§6.1) — a stronger form of the RFC's "late binding", because the destination is never resolved to an address anywhere in the network, only recognized by the key holder at delivery time. The RFC's bundle-layer *mechanisms*, on the other hand, are almost all deliberately absent: there is no Bundle Protocol (the six-field envelope is a minimal, encrypted substitute), no routing or forwarding decisions (nodes never talk to each other — human mobility is the only transport), no custody transfer or retransmission, no priority classes, no bundle-layer administrative records, no hop-by-hop security, and no synchronized-clock requirement beyond a 300-second admission skew. The role RFC 4838 gives to a single "bundle layer" is in Offgrid split three ways: the browser SPA is the bundle agent (composition, signing, reassembly, delivery state), the envelope format is the bundle format, and the physical movement of people is the convergence layer. Every one of these deviations is a consequence of one design decision — **zero-trust, blind intermediaries** (protocol.md §1, §13) — and nearly all are recorded in the normative spec today. The audit found **one unintentional gap** (outer envelope metadata — `dest_hint`, `created_at`, `ttl` — is not authenticated end-to-end and clients do not verify the `id`-to-content binding on receipt; §6.4 below) and a handful of over/under-statements in `README.md`, corrected by this PR.

Verdict counts (rows 1–16, fixed scale of §2): **Aligned 2 · Partial 10 · Deviation (intentional) 4 · Deviation (unintentional) 0 · Not applicable 0.** Sub-row findings classified in the deviation register (§6): 10 intentional, 1 unintentional (needs a follow-up issue).

## 5. Per-concept discussion

### 5.1 Row 1 — Store-and-forward (§3.1): genuine, and atomic

The RFC's core assertions: ADUs become bundles; bundles wait in queues until a contact appears; storage is persistent and survives restarts; bundles carry timestamp, lifetime, and length. Offgrid satisfies each: an envelope is one immutable JSON object (§3: "The atomic unit of transport… Immutable once created"); it waits in node SQLite (WAL journal mode "survives power loss on solar-powered nodes", §9) and in the mule's IndexedDB `transit_queue` (which persists across portals because every node serves the same web origin, §12); every envelope carries `created_at`, `ttl`, and an exact `payload` length bound (§8.2). The full journey — Alice → node A → mule → node B → Bob with byte-identical payloads — is pinned end-to-end by `tests/sync_e2e.sh` (sha256 of the payload asserted through the mule).

Does the system *genuinely* implement store-carry-forward across disconnected islands? Yes — with the honest caveat that the "carry" leg is not a network hop at all: nodes never talk to each other (§2), so the only thing that ever crosses the gap between two islands is a person. RFC 4838's store-and-forward assumption 1 ("storage is available and well-distributed throughout the network") is met by construction: every phone that opens a portal is distributed storage.

**Atomicity of an envelope in transit — what actually happens when a mule's IndexedDB write is interrupted.** Three levels:

- *Node side:* a sync batch is inserted in a single SQLite transaction (`storage.go` `InsertEnvelopes` — one `BEGIN`…`COMMIT` around the whole batch), under WAL. A crash mid-write rolls the batch back whole; a power loss replays or discards at the WAL boundary. There is never a half-stored envelope — the row either exists (all six fields) or does not. The chaos suite (`tests/chaos/chaos_kill_mid_sync.sh`, `chaos_restart_under_load.sh`) pins degrade-and-recover behavior.
- *Mule side:* IndexedDB writes are transactional per object store; each envelope is one record, so an interrupted write leaves either the old or the new record, never a fragment. The sync cycle only removes an envelope from `transit_queue` after its push chunk succeeded (`ui.js` `runSync`: "failed chunks stay and retry on the next sync"), so an interruption at any point degrades to **at-least-once carrying** — the worst case is a duplicate push, which the next node's `INSERT OR IGNORE` absorbs.
- *Wire side:* an envelope is one JSON document validated whole before storage (§10.5 fail-closed: any invalid envelope rejects the entire batch). No parser on any path ever materializes a partial envelope.

So the atomicity guarantee is: **an envelope is never observed in a partial state by any component; the only interruption effect is re-delivery, which dedup makes a no-op.** This is exactly the RFC's model ("ADUs are typically sent by and delivered to applications in complete units"), and the RFC's warning that "the relative order of ADUs might not be preserved" is equally true here (ordering is display-only, via the sender-authored inner `t`).

### 5.2 Row 2 — Nodes, endpoints, EIDs, registrations (§3.2, §3.3)

**What the RFC defines.** A node is an engine for sending/receiving bundles and MUST have at least one unique EID; an endpoint is a named set of nodes (with a minimum reception group); an EID is a URI; a registration is an application's persistent declaration "deliver ADUs for EID X to me". §3.3.2 defines *late binding*: the destination name is re-interpreted per hop, because in a frequently-disconnected network a source-time binding may outlive its validity.

**What Offgrid has instead.** There is no EID namespace, no URI scheme, no node identity, and no bundle-layer registration. The endpoint unit is a *key pair*: identity = Ed25519 (signing) + X25519 (encryption); addressing = `dest_hint`, the truncated HKDF of the X25519 public key under the current day-epoch (§6.1). A "registration" has two shadows: publishing a directory entry (`POST /api/v1/directory` — a persistent, server-side record of *key material*, never consulted by the envelope path, §10.5) and the recipient's local candidate-set recognition (`{legacy, hint(E), hint(E−1)}` — the client-side "which mail is mine" check, §11). Delivery is defined by *possession*: an endpoint is whoever holds the X25519 secret — an MRG of one, unforgeable, with no group semantics (row 3).

**Late binding, honestly assessed.** Offgrid is *later*-bound than the RFC's own mechanism in the dimension that matters for disrupted networks — the destination is never bound to a location or next hop anywhere, ever: an envelope deposited at node A is claimable at any node by whichever key holder arrives. But it is *earlier*-bound in a different dimension: the hint is fixed at creation time from the recipient's key + epoch, and cannot be re-interpreted in transit (it is inside what the recipient matches, and rotating hints are deliberately not re-derivable by intermediaries). The RFC's motivation for late binding — "the transit time of a message may exceed the validity time of a binding" — is handled instead by the epoch-rotation design: a binding's validity is exactly two epochs, and the candidate set covers exactly one boundary crossing (§6.1). Issue #26 is the design record.

**Is a 64-bit hint's collision behavior acceptable? Yes.** `dest_hint` is 8 bytes (§3.1: 16 hex chars). Two distinct users sharing a hint would cause the node to serve one's envelopes to the other's pulls (the select is `WHERE dest_hint = ?`, §10.4). The consequences are bounded by cryptography, not by luck: a collided envelope fails the collision victim's trial-decrypt (the XSalsa20-Poly1305 MAC cannot verify under the wrong key) and is **silently discarded** (§4.3) — so the failure mode is silent loss of that one envelope, never mis-delivery of readable content. The probability is birthday-bounded: for a community of *n* users on one node it is ≈ n²/2⁶⁵ — at 10,000 users ≈ 2.7×10⁻¹²; at a realistic site (hundreds) it is astronomically smaller. Rotation (issue #26) does not change the collision space (same 64 bits, fresh derivation per epoch, so a collision persists only within an epoch pair and re-rolls each day). Verdict: acceptable, with the reasoning above recorded here for the first time.

**Node EIDs: absent by design.** Nodes are anonymous, interchangeable dead-drops; there is no node-to-node protocol to authenticate to, and identifying nodes would create exactly the persistent linkability surface §13 avoids. This is an intentional deviation recorded by §1 (blindness) and §13.

### 5.3 Row 6 — Primary bundle fields (§3.7)

The RFC lists the primary-block fields every bundle carries. The explicit mapping:

| RFC 4838 primary-block field | Offgrid counterpart (protocol.md §3.1, §4.1) | Mapping notes |

| Creation timestamp (time + sequence number, unique per ADU per source) | `created_at` (unix seconds, ≤ 300 s future skew) + `id` (SHA-256 of the canonical §5.2 string) | Uniqueness comes from **content**, not a sequence number: identical content yields an identical `id`, which is what makes dedup work; there is no per-source counter to synchronize. | Lifespan (offset from creation) | `ttl` ∈ [3600, 2592000] s; absolute deadline = `created_at + ttl` | Enforced twice: inclusive serving boundary (§10.4) and exclusive janitor delete (§10.6) — "either servable or deleted, never in limbo". |

| Integrity (BP: CRC over blocks; BPSec: signatures) | Poly1305 MAC + Ed25519 signature, **both inside the box**; `id` is a content hash | The `id` is a *dedup key with a semantic bonus*: it is the hash of the canonical outer fields, so it *could* serve as an integrity check on them — but nobody recomputes it (see the gap below). |

**The sign-then-encrypt inversion, called out explicitly.** In BP, the primary block — version, source, destination, report-to, custodian, timestamps, lifetime — is *plaintext by design*: every node on the path is supposed to read it to route, report, and take custody. Offgrid inverts this for source and destination: sign-then-encrypt (§4.2) puts the sender's identity inside the ciphertext and reduces the destination to an unroutable 64-bit token. The consequence is that most of what BP's primary block enables *cannot exist* here — routing (nothing to route on), status reports (the node cannot even tell delivery from non-delivery), custody (no accountable custodian identity), access control (no names to check). This is not an omission from the mapping; it is the mapping: **whatever the RFC's primary block exposes, Offgrid hides on purpose, and whatever functionality that exposure bought is either relocated to the endpoints (acks) or deliberately surrendered.** The only outer fields that remain network-visible are the minimal set a blind dead-drop needs: the hint (to index), the timestamps (to expire), and the id (to dedup).

**The unintentional gap.** Outer metadata (`dest_hint`, `created_at`, `ttl`) is not covered by any end-to-end cryptographic check. The inner signature covers `m, a, k, t` (+ chunk/ack metadata) only; the MAC protects only `payload`. A hostile node or mule *can* rewrite the outer metadata of an envelope it carries — lower `created_at` or raise `ttl` (both within admission bounds) to extend an envelope's life, alter `dest_hint` to misroute it into unclaimability, or mint id-mutated copies of a payload to duplicate a delivered message in a recipient's inbox. Nothing detects this today: the spec forbids the *node* from recomputing `id` (§6.2, for interop), and the *client* validates only the id's shape on receipt (`envelopes.js` `validEnvelopeShape`). Impact is confined to availability/quality-of-delivery (life extension, loss, duplicates) — confidentiality and authenticity are untouched — but it is a real gap against the "promptly discard bundles that are damaged or improperly modified in transit" goal of §3.14, and §13.2's node row ("cannot alter envelopes (Poly1305 MAC)") overstates the guarantee: nodes cannot alter *content*; they can alter *metadata*. Classification, remediation, and the proposed follow-up issue: register §6.2.

### 5.4 Row 7 — Routing and forwarding (§3.8)

There is nothing to map: no routing algorithm, no RIB/FIB, no contact graph computation, no next-hop decision — the deviation is the design (§2: "Nodes never talk to each other; all transport between nodes is physical"). In the RFC's vocabulary the actual model is:

- **Contacts:** every delivery opportunity is an *opportunistic contact* (§3.8.1) — a human opening a captive portal — with zero predicted or scheduled contacts. The time-varying multigraph of §3.8 exists, but its edges are mule walks and no node ever computes over it.
- **Forwarding:** trivially "hand everything to every opportunity": a mule pulls all envelopes its `known_ids` exclude (up to `limit`), carries them, and pushes them at the next portal. There is no decision to make because there is no next hop to choose.
- **Replication semantics:** the scheme is *not* single-copy. When a mule departs node A, the envelope stays in A's dead-drop until TTL expiry (§10.6); every subsequent mule can carry another copy. The dead-drop network is a set of replicated sources with garbage collection, and copies converge on recipient-side id dedup. Loop risk — the classic epidemic-routing pathology — is bounded structurally: nodes never exchange envelopes with each other, so replication depth is 1 (node → mule → node), and TTL + id dedup clean up the rest.
- **Routing state:** none, anywhere. The closest thing to forwarding state is the mule's `transit_queue` and the node's `dest_hint` index (§9) — an index for *retrieval*, not routing.

Characterized precisely: **mobility-based opportunistic transport with dead-drop replication and TTL garbage collection — "routing" delegated to human behavior.** Intentional, recorded in §1/§2 and frozen by §14.1 (no routing fields will be added; `hop_count` is reserved for the Phase 2 phone-to-phone mesh, the one planned case where a relay decision will exist).

### 5.5 Row 8 — Fragmentation and reassembly (§3.9) and issue #24's chunking

The RFC defines two forms. **Proactive**: a source divides a large ADU into independent bundles, and *the final destination* reassembles — used when contact volumes are known or predicted. **Reactive**: nodes split a bundle cooperatively after a partially-transferred transfer; the RFC itself flags that reactive fragmentation "presents significant challenges with respect to handling digital signatures… when a signed message is only partially received, most message authentication codes will fail."

Offgrid's §4.4 chunking (issue #24) is **proactive fragmentation in the RFC's exact sense, relocated into the application layer**: the sending client splits a >128-byte text into ≤ 16 ordinary envelopes (each a complete, self-sufficient envelope with its own ephemeral key, nonce, TTL), each chunk carries *signed* reassembly metadata (`w, g, i, n`) inside the box, and the final destination reassembles — keyed by the group id `g`, out-of-order tolerant, duplicate-tolerant (first write per index wins), with partial state rendered as "message i+1/N — still traveling" and expiring with the chunks' shared TTL (`chunking.js`, `store.js` `inbox_parts`; pinned by `tests/chunking.mjs` and the chunking section of `tests/sync_e2e.sh`). The mapping is faithful on every axis the RFC names: split point (source), reassembly point (destination only — RFC allows anywhere; here nowhere else *can*, since intermediaries cannot read the pieces), and independence of fragments (each chunk is deliverable and TTL-expirable alone).

**Reactive fragmentation is categorically impossible**, and for exactly the reason the RFC gives: the envelope is atomic, opaque, and MAC-protected — an intermediary cannot know it carries a piece of anything, and a partially-received envelope cannot be split because nobody on the path can see inside it. Sign-then-encrypt realizes the RFC's caveat as a design invariant.

**Partial-delivery failure modes (the honest cost).** Chunks are independent envelopes, so a message is only as deliverable as its least lucky chunk: a chunk lost to mule FIFO eviction, TTL expiry, a full node, or the §4.6 prekey windows leaves the partial incomplete — the message never renders, the partial expires silently with the shared TTL, **the sender is never informed** (acks fire only at reassembly completion, §4.5), and there is no retransmission of missing pieces. Loss probability grows with chunk count (up to 16) and queue pressure; the composer's pre-send "will send N envelopes" preview and the N ≥ 8 warning (§4.4) make that cost visible and user-approved before it is incurred. This is the deliberate trade: no network-layer reliability (row 9) means no fragment recovery either.

### 5.6 Row 9 — Reliability and custody transfer (§3.10): what duplicate sync actually does

**Custody transfer** — moving retransmission responsibility among identified custodians with custodian-to-custodian signaling — is absent wholesale, and cannot be reconciled with the design: a custodian needs an identity to be accountable, and Offgrid nodes have none (row 2); a custody signal needs an authenticated return channel, which blindness forbids (§13.2). Offgrid's substitute reliability strategy has three pieces:

1. **Replication instead of retransmission.** Envelopes persist at every node they touch until TTL expiry; a lost mule does not lose the mail. Storage is the reliability.
2. **At-least-once transport + universal id dedup.** Every store dedups on `id` (`INSERT OR IGNORE`, §6.2/§10.4), clients dedup via `known_ids` (inbox ∪ transit ∪ permanent `seen_ids` ∪ pushed ids, §11, `ui.js` `runSync`), chunk reassembly tolerates duplicates, and ack application is idempotent (`ackMatchesSent`, "already-applied ack silently ignored").
3. **Best-effort end-to-end acks** (§4.5, issue #25) — the only delivery feedback, explicitly "best-effort, never a read receipt".

**What duplicate `POST /api/v1/sync` actually does — verified hands-on (method §2):** the duplicate batch answers `200` with the identical response shape; the already-stored rows are absorbed by `INSERT OR IGNORE` (the store reports the absorbed count as `dedup_hits`, §10.7); nothing is duplicated, nothing is rejected. The duplicate pusher is *also* still served pull results per its `known_ids`: the node **re-serves a live envelope on every pull whose `known_ids` do not cover it** — node-side dedup is about storage, delivery dedup is entirely client-side. This division is deliberate: it keeps the node stateless about clients (no per-client delivery bookkeeping = no state that could leak or persist).

**Residual silent-loss modes (all documented, none signalled):**

- Mule `transit_queue` FIFO eviction at 100 envelopes, oldest `created_at` first (§8.1, `mule.js` `evictTransitQueue`) — the evicted envelope is dropped without any report to anyone.
- TTL expiry at a node before any recipient-compatible pull (§10.6) — "expiry is the DTN equivalent of return-to-sender" (§10.5), i.e. silence.
- Node-full shedding (`429 node_full`, reject-newest/keep-oldest §8.1) — visible to the *pushing mule*, invisible to the original sender.
- §4.6 prekey windows (OPK collision; replenish-away) and §6.1 epoch windows (mail older than two epochs is unrecognizable) — both bounded, both documented as accepted (§13.5).
- Browser data wipe (identity, inbox, and carried mail all lost) — mitigated only by manual seed backup (§11).

Verdict: intentional deviation, driven by zero-trust (the rationale recorded in §1, §4.5, §13.5); the honest summary for users is already in the docs: delivery feedback is best-effort, and silence means *unknown*.

### 5.7 Rows 10 & 16 — Gateways/proxies (§3.11) and convergence layers (§6): does "evolution without rewrite" hold?

The RFC's §6 construct — convergence layers that "manage the protocol-specific details… and present a consistent interface to the bundle layer" — is exactly what protocol.md §14 defines: frozen semantic fields (§14.1 rule 1), transport-tier encodings (rule 3: hex/Base64 text in Phase 1, raw bytes in CBOR in Phases 2/3, conversions lossless), a full JSON→CBOR field table (§14.2), and pre-computed size math against the LoRa 222-byte MTU (§14.3). The claim is anchored in the code at every place a developer touches the envelope (§14.4: `envelope.go` type doc, `index.html` above `buildEnvelope`).

**Would the envelope format actually survive a convergence-layer change? Yes, by construction — with three honest reservations:**

1. **The signed inner changes form, not just encoding.** Phase 2/3 define a canonical *CBOR* inner (§14.2) — a new signed byte string. The 1:1 field mapping makes the transformation mechanical, but the CBOR form must be pinned byte-exactly (worked vectors, §15-style) or signatures will not cross phases. Nothing new to design; something to pin.
2. **Admission rules are CL-binding today.** §10.5's regexes (hex id, hex hint, padded Base64) are Phase 1 text-encoding facts; a new CL needs its own blind admission rules under the §15.3 versioning policy — provided for, not yet written.
3. **The LoRa short-message mode genuinely diverges**: it omits `id`, `dest_hint` and `alias` and broadcasts to every receiver for trial-decrypt (§14.3b), with `id` recomputed from frame bytes — a real CL-specific identification rule, of exactly the kind the RFC says convergence layers exist to absorb.

Per-CL compatibility of the binding limits (the issue's row-16 question):

| Limit | BLE L2CAP CoC (Phase 2) | LoRa P2P 915 MHz (Phase 3) |
|---|---|---|
| Payload decoded [248, 400] B → binary envelope 244–399 B (§14.3) | One SDU: negotiated MTU ≥ 512 B fits the max envelope + 2-byte length prefix; L2CAP does segmentation | 2-frame general mode: 2 × 221 = 442 ≥ 399 (§14.3a); or 1-frame short mode for M ≤ 48 |
| TTL range [3600, 2592000] s | CBOR uint, 3 bytes — unchanged | Same; short mode carries a 4-byte `ts` instead |
| `id`/`dest_hint` encodings | bstr(32)/bstr(8), lossless decode of the hex forms (§14.1 rule 3) | Omitted in short mode (broadcast trial-decrypt); general mode as in BLE |
| Reliability below the bundle layer | Credit-based flow control at L2CAP; link-layer ARQ | None — frame loss = envelope loss, accepted (envelopes are expendable, TTL-bounded, id-dedup'able) |
| Inflation | n/a (binary) | n/a (binary); the Phase 1 Base64/hex inflation (~33%) is exactly why §14.3 exists |

§3.11's own topic — proxies and application-layer gateways for *existing Internet applications* — has only a light analog: the captive portal + same-origin trick is the HTTP↔human boundary, and the node's public read surfaces (`/guide`, `/status`) serve non-DTN clients, but Offgrid runs no foreign-protocol gateway over the DTN, and the RFC's application-acknowledgment mechanism for remote gateways corresponds to §4.5's acks (row 5). Partial is the honest verdict for both rows: the architecture provisions CL adaptation normatively; validation beyond one shipped CL is design analysis, not experience.

### 5.8 Row 11 — Timestamps and time synchronization (§3.12)

The RFC depends on node clock synchronization for four purposes; Offgrid's handling of each:

1. **Bundle/fragment identification** ("EID, timestamp, and data offset/length together uniquely identify a bundle"): solved **clock-free**. The `id` is a SHA-256 of the content (§6.2) — uniqueness comes from the hash, not from a (source, timestamp) pair, so identification survives any skew. Fragments identify by signed group id `g` (§4.4).
2. **Routing with scheduled/predicted contacts**: not applicable — no scheduled contacts exist (row 7).
3. **Bundle expiration**: *approximate by design*. Every store computes `created_at + ttl` against its own clock (§10.4/§10.6); the only normative bound is the 300-second future-skew admission check (§3.1, `ClockSkewSeconds` in `envelope.go`). A fast sender clock extends an envelope's effective life by up to the skew; inter-node drift shifts the deadline per store independently. A Pi without RTC or NTP drifts unbounded over weeks — the docs accept this implicitly (TTL is "about" 7 days, janitor every 15 minutes) but nowhere bound the drift; that is honest to state here: **TTL is a best-effort lifetime under unsynchronized clocks, and the RFC's own reliance on "basic time synchronization… supported by external, non-DTN protocols" is simply not assumed.**
4. **Application registration expiration**: not applicable — no registrations (row 2). The nearest analog, directory `last_seen`/`epoch`, is stamped by the *node's* clock at upsert (§10.3), deliberately making the node the shared time reference for hint rotation (§6.1: "nodes have no NTP — the NODE's clock is the shared reference").

**Skew implications for ordering and expiry fairness.** Ordering: pull results are `ORDER BY created_at DESC` (`storage.go`), i.e. by sender clocks; inbox display uses inner `t`. There is no global ordering and the RFC requires none ("the relative order of ADUs might not be preserved") — but a fast clock both *sorts earlier* and *lives longer*, so skew systematically favors fast-clock senders in both queue position and lifetime. The §4.3 step-6 client-side check ("optionally reject as corrupt if `t` is more than 300 s in the future") bounds the visible absurdity, not the mechanics. The epoch design (§6.1) is the one place skew has protocol consequence — and it is handled structurally: senders derive hints from *directory* epochs (never their own clock), recipients tolerate a two-epoch window, and a node whose clock runs truly sideways would rotate hints against every other node's epochs — the candidate set covers ordinary drift; a badly-sick node degrades to undeliverable rotating mail (legacy static hint only during the transition window), a failure mode an operator sees via `/status` (§10.7). Partial verdict: timestamps and lifetimes exist and are enforced; synchronization is deliberately replaced by bounded skew + structural tolerance.

### 5.9 Row 12 — Congestion and flow control (§3.13)

The RFC's definitions: flow control keeps a sender from outrunning a receiver; congestion control keeps aggregate injection under network capacity; a bundle node's degrees of freedom are discard-expired, refuse custody, and (last resort) discard non-custodied bundles. Offgrid's answer is pure §3.13 "discard as early as possible", minus the signaling:

- **Admission control** (per-IP request + envelope budgets, `429 rate_limited` + `Retry-After`, §10.1) — checked *before* the body is read, so a flood costs the node almost nothing.
- **Storage ceiling** (5000 envelopes, `429 node_full`) with the deliberate **reject-newest/keep-oldest** policy (`storage.go` `maxEnvelopes` doc: nothing accepted is ever evicted except by the TTL janitor) — under a flood, the flood's fresh junk is refused and legitimate old mail keeps being served. This is the RFC's "discard bundles which have not expired but for which it has not accepted custody" degree of freedom, realized as "refuse at the door" — Offgrid never accepts custody, so it never has to break a custody promise.
- **Mule-side capacity** (100-envelope FIFO, §8.1): the true silent loser under congestion — a mule overloaded by a chunk-heavy or busy site silently evicts oldest cargo.
- **No backpressure to senders exists.** A mule cannot learn a node is nearly full before pushing; the first signal is the `429` after the fact. (`Retry-After` is a primitive per-client pacing signal, but it is admission-level, not storage-level.)

**Is any flow-control signal compatible with the blind-mailbox model? Yes — and one already ships.** The health snapshot (§10.7) publishes aggregate store fill (`envelopes`, `envelope_capacity`, `expiring_within_1h/6h/24h`, projections) with *no* per-envelope, per-alias, or per-address data — reviewed against §13 for exactly that property. A future client could throttle its pushes or prefer less-loaded nodes from those aggregates without introducing an oracle. What is missing is any normative client behavior keyed on them; today they inform operators, not mules. Silent-loss-under-congestion semantics: documented (reject-newest/keep-oldest; FIFO eviction; §13.6 store-flooding row). Partial verdict, matching the issue's expectation.

### 5.10 Row 13 — Security (§3.14, §8): the mapping, and the replay question answered

Mapped threat-by-threat onto the RFC's concerns (Offgrid's own model: protocol.md §13):

| RFC 4838 security concern | Offgrid mechanism | Assessment |
|---|---|---|
| Authenticity of principals ("end-to-end authentication for a principal") | Ed25519 signature over the inner payload, sign-then-encrypt (§4.2, §4.3 step 5); recipient-only verification | **Aligned in effect** — arguably stronger than typical BP deployments because it is always-on, never optional. |
| Authenticity of nodes ("hop-by-hop… authenticate DTN nodes as legitimate transceivers") | **Deliberately absent.** Nodes are anonymous; the network has no membership | Intentional deviation: access control is replaced by blindness + budgets/caps (§13.6). The RFC's "promptly prevent unauthorized applications from having their data carried" is answered differently: *everyone* is authorized to carry, nobody is able to read. |
| Integrity in transit | Poly1305 MAC on the payload + Ed25519 over the inner; outer metadata unprotected (see §5.3) | Partial — content integrity strong end-to-end; metadata integrity missing client-side verification. |
| Confidentiality | XSalsa20-Poly1305 with per-message ephemeral keys (§4.2, §7); §4.6 prekeys bound the capture-now/decrypt-later horizon | Strong; forward secrecy bounded and honestly stated (§4.6 rule 4, §13.5). |
| Availability / infrastructure protection | Blindness (no discrimination data exists), admission budgets, node cap, janitor, hardening tracks (§13.6, `docs/hardening.md`) | Meets the RFC's "discard as quickly as possible" goals by construction: the node *cannot* prioritize or filter what it cannot read, so DoS resistance is purely quantitative (caps/budgets) plus operational (firewall tracks). |
| Promptly detect/de-authorize compromised entities | None. No revocation, no key transparency; directory entries unauthenticated end-to-end (the doctored-bundle note, §13.5) | Documented acceptance; key transparency explicitly out of scope. A compromised *key* is indistinguishable from its owner — the reciprocal cost of anonymous infrastructure. |
| Replay | **No explicit mechanism.** Analysis below. | Documented acceptance (§13.5); deviation register row 13. |

**Is there ANY replay defense today? Analyzed honestly: no mechanism; a construction that makes replay mostly harmless.**

The issue is right to warn that `id`-based dedup is not replay protection and TTL does not prevent replay within its window. Precisely:

- *What dedup is:* `INSERT OR IGNORE` prevents duplicate **storage**; `known_ids`/`seen_ids` (a permanent per-device memory, `store.js` `seen_ids` "dedup memory of every envelope id ever pulled or pushed") prevents duplicate **delivery** to the same client state. Neither authenticates *when* an envelope was injected or by whom.
- *The replay scenarios, one by one:*
  1. **A node re-serves an old (unexpired) envelope** to a mule: §13.5's exact case. The client has the id in `seen_ids` forever → never re-delivered; if state was wiped, re-delivery is indistinguishable from mule re-carry (and harmless — same bytes, MAC-checked, first-write-wins in reassembly).
  2. **An adversary re-injects a captured envelope into a node within its TTL window:** admitted (validation has no freshness *lower* bound), stored as a duplicate id (absorbed), or as a new node's fresh copy — delivered once to the recipient whose state lacks the id, then never again. Cost: bandwidth/storage (budgeted), no semantic harm.
  3. **Re-injection after TTL expiry:** admitted (no lower bound!) but never served (§10.4 inclusive boundary) and swept by the janitor (§10.6) — inert garbage, verified hands-on in the method's spot check (the 2025-dated §3.2 vector was accepted and never served).
  4. **Metadata-mutation "replay"** (id-mutated copies of the same payload to dodge dedup): possible precisely because outer metadata is unauthenticated — the §5.3 gap; a fresh id *is* a new envelope to every dedup, so the recipient sees a duplicate inbox entry. Bounded impact (annoyance/queue pressure), closed by the same proposed fix (client-side id recomputation).
  5. **Ack replay:** a captured `ack1` re-delivered later binds via `ackMatchesSent` to a specific sent record (recipient key + reference id); application is idempotent; a re-*sent* message has a new `created_at` hence a new `id`, so an old ack cannot flip a new record. Safe by binding, not by freshness — worth stating, since §4.5 never uses the word replay.
- *Net:* within any window in which the recipient's local state persists, replay converges to a no-op; outside it, replay is inert (expired) or is the metadata-mutation case. There is no scenario today where replay forges, alters, or un-delivers mail. **Classification: Deviation (intentional)** — §13.5 documents the re-serve case as "harmless" with the dedup+MAC rationale, which the analysis above extends to the injection cases. Recommendation: **accept; no follow-up issue required for replay per se.** The candidate follow-up that *is* warranted is the §5.3 metadata-integrity fix, which also removes scenario 4. A one-sentence precision touch-up of §13.5/§13.2 (saying TTL does not prevent replay within its window but state-based dedup + expiry do bound it) can ride along with that issue's docs.

### 5.12 Row 15 — Application structuring (§5)

RFC 4838 §5 asks applications to be asynchronous, self-contained, restart-tolerant, and explicit about lifetime/importance. The Offgrid SPA is a reference implementation of that advice:

- **Asynchronous, message-oriented:** sending never blocks on a network outcome — the composer builds envelopes locally and sync happens on page load plus manual trigger (§11; `ui.js`: "§11: sync automatically on page load"). Zero round trips are ever assumed; the ack (§4.5) is itself an asynchronous message.
- **Self-contained ADUs:** the whole message + signature + (chunk) reassembly metadata travels inside one envelope; a chunked message's pieces are individually meaningful to the transport and only jointly meaningful to the application — the RFC's "include enough information in an ADU so that it may be treated as an independent unit of work" holds at both layers.
- **Restart tolerance:** "an application may terminate between the time it sends a message and the time it expects a response" is not the exception here but the *normal* case — a captive-portal page closes within minutes, while its mail travels for days. Queued sends and carried cargo persist in IndexedDB and ride the next sync; sent-state tracking (`queued → sent → delivered`) persists in the `sent` store. No service worker exists (§12.1's honest boundary), so the application only works while open — which is why nothing in the protocol depends on it being open.
- **Informed network:** TTL is mandatory per envelope (the format has no default-sender escape; the client defaults to 7 days). Importance is not expressible (row 4) — the one structuring advice unmet, intentionally.

What an application developer must know (the issue's question), all documented: the 128-byte-per-envelope plaintext limit with client-side chunking to 16 envelopes; at-least-once-ish semantics (duplicates possible in transit, absorbed by dedup); no delivery guarantee and best-effort acks whose silence means unknown; no ordering guarantee (`t` is display-only); the 300-second skew rule for `created_at`; TTL bounds [1 h, 30 d]; and the capacity cost model (chunking preview, 100-envelope mule queue). Aligned.

### 6.2 Unintentional deviations (needs follow-up issue)

**U-1 — Outer envelope metadata is not authenticated, and clients never verify the `id`-to-content binding.**
Found in: row 6 (§5.3) and the replay analysis (§5.10, case 4). `dest_hint`, `created_at`, `ttl` travel as plaintext, network-visible fields covered by no MAC and no signature; the inner Ed25519 signature stops at `m, a, k, t` (+ inner conventions), and the client validates only the id's *shape* on receipt (`node/web/js/envelopes.js` `validEnvelopeShape`) — the spec forbids the *node* from recomputing `id` (§6.2) but never asked the *recipient* to. Consequences (all availability-class, none confidentiality/authenticity-class): in-transit life extension via `created_at`/`ttl` mutation; misrouting via `dest_hint` mutation (silent loss); id-mutated duplicate injection (dedup bypass → duplicate inbox entries). Related wording overstatement: §13.2's node row says a node "cannot alter envelopes (Poly1305 MAC)" — true of content, not of metadata.
**Proposed remediation path (no code changed by this audit):** have Module C clients recompute the §5.2 hash of received envelopes and silently discard mismatches (cheap, local, purely post-decryption, blindness-preserving — the node stays out of it entirely); specify it as a client MUST (or SHOULD with the legacy transition considered) plus the §13.2/§13.5 wording precision. The §15.7 matrix gains a tamper row.
**Proposed follow-up issue:** title *"Client-side envelope-id verification on receipt: detect in-transit metadata mutation (RFC 4838 audit U-1)"* — scope: Module C verification + protocol.md §4.3 step, §13.2/§13.5 wording precision + §15.7 test row; labels `documentation`, `enhancement`.
**Classification note:** recorded as unintentional because no spec section or design record claims metadata is protected; it is a consequence of the format's layering nobody wrote down — exactly what this audit exists to catch.

## 8. What BP conformance would mean, and why not

Offgrid intentionally does not speak RFC 5050/9171, and making it do so would not be an upgrade — it would be a different system. Adopting BP means: a visible primary block (source, destination, report-to, custodian) on every hop — repealing the sign-then-encrypt inversion that §13's entire threat model is built on, or restoring it piecemeal via BPSec confidentiality blocks, which would put BP's plaintext metadata *plus* encryption overhead on a 222-byte LoRa MTU that §14.3 already fights for bytes on; bundle agents and registration state where anonymous dead-drops now stand; custody and status-report machinery that blindness forbids; and an interop obligation (canonical BPv7 CBOR, CRCs, extension blocks) whose only payoff would be talking to BP nodes that, in the target deployment (isolated islands with no uplink), do not exist. The DTN architecture is the part of RFC 4838 that earns its keep here — store-carry-forward, lifetimes, opportunistic contacts, endpoint naming — and Offgrid takes all of it while discarding the protocol that was designed for a different trust model (infrastructure-assisted, node-identified, administratively operated). The defensible position, which this audit verifies row by row, is the one the project already holds: **architecture-conformant, protocol-independent.** If interop with external BP networks ever becomes a requirement, the honest path is a convergence-layer-style gateway speaking BP at the edge — §14's extension pattern — not a rewrite of the envelope.
